# dawg-replay-builder

Ты один раз проходишь путь по сайту через браузер DAWG (`dawg-mcp`) и превращаешь его в скрипт `script.py` по контракту `dawg-replay`. Дальше скрипт работает без тебя: клиент запускает его в приложении, меняет параметры и платит только минутами DAWG.

Скрипт собирает данные (раздел A), делает действия на сайте по строкам таблицы клиента (раздел B) или одно действие и проверку страницы без таблицы (раздел D). Несколько скриптов, где результат одного идёт на вход другому, соединяются связями в приложении (раздел E). Приложение ничего не навязывает: что скрипт принимает на вход, как его запускают и что он отдаёт, ты договариваешься с клиентом (раздел 1) и объявляешь в манифесте.

Справочные файлы рядом:

## 0. Проверка окружения (всегда первым шагом)

1. Инструменты браузера DAWG: среди твоих инструментов есть `browser_provision`, `browser_navigate`, `browser_snapshot`, `browser_release` с любым префиксом сервера (`mcp__dawg__browser_provision`, `mcp__plugin_..._dawg__browser_provision` и так далее). Нет таких инструментов: `dawg-mcp` не подключён.
2. Приложение: `dawg-replay --version --json`. В `contract_versions` должна быть `1.3`, для связей между скриптами и блока `outputs` (раздел E) ещё `1.4`. Команда не найдена, поля нет или нужной версии нет: приложение не установлено или старое (`uv tool upgrade dawg-replay`).
3. Ключ: `dawg-replay --json config show`, поле `api_key_set`. `false`: попроси клиента выполнить `dawg-replay config set-key` (или ввести ключ в UI на экране Настройки). Ключ сам не вводи и не проси прислать его в чат.

Если 1 или 2 не выполнены, объясни клиенту, что поставить, и дальше не иди (пункт 1 нужен для разведки сайта; задаче без сайта, например обработке файла или вызову API клиента, хватает пункта 2):

- `dawg-replay`: `uv tool install dawg-replay`, нужен `uv` (https://docs.astral.sh/uv/) и Python 3.10+.
- `dawg-mcp` в Claude Code: плагин `dawg-replay-builder` подключает его сам; вручную `claude mcp add dawg --scope user --env DAWG_API_KEY=<ключ> -- uvx --with 'mcp<2' dawg-mcp`. В Codex: блок `[mcp_servers.dawg]` в `~/.codex/config.toml` (см. README плагина). После подключения перезапусти сессию.

## Черновики: каждый скрипт в своей папке

Сессия может работать над несколькими скриптами, поэтому черновик каждого лежит отдельно: `./<name>/script.py`, где `<name>` это `name` из манифеста (slug, например `ozon-prices`). Рядом можно класть заметки разведки. Все команды `validate`, `run`, `add` получают путь `<name>/script.py`.

- Перед записью проверь папку. Её нет: создай. В ней `script.py` с другим `name` в манифесте: это чужой черновик, спроси клиента или возьми другое `name`.
- Приложение при `add` хранит свою копию, черновик ему потом не нужен.

## 1. Разговор: что делаем, вход, запуск, выход

Общий для любой задачи и идёт перед разделами A, B и D. Не больше 2-3 вопросов за раз; очевидное выбери сам и скажи, что выбрал.

1. Что делаем: собрать данные, сделать одно и то же по списку, одно действие или проверку страницы. От ответа зависит шаблон: A, B или D. Если в задаче несколько шагов, где результат одного нужен другому («собрать цены WB и Ozon, потом обновить мои цены, потом отчёт»), это цепочка: несколько скриптов и связи между ними (раздел E), а не один большой скрипт. Выясни это до сборки и скажи клиенту, какие скрипты получатся.
2. Как клиенту удобно давать данные. Предложи подходящее и спроси:
   - отдельные поля формы: текст, число, выбор из вариантов (`enum` с понятными подписями `{ value, title }`, несколько вариантов сразу `multi_enum`), да/нет;
   - даты: точная или «за вчера», «с начала месяца», «прошлый месяц» (относительная дата, `default = "today-1"`): для регулярного запуска почти всегда относительная, иначе каждый раз одна и та же дата; время и дата со временем (`time`, `datetime`);
   - список строк: таблица Excel, CSV, TSV или JSON файлом на каждый запуск, ввод одной-двух строк руками, таблица в пресете для расписания (`table`, `input` перечисляет только нужные способы, `sheet` для нужного листа Excel, `column_types` для чисел и дат);
   - документ, картинка или архив на входе (`file` с `accept` и `max_mb`), ключ или сертификат сервиса (`file` с `secret = true`); пароли и токены (`secret` или таблица с `secret = true`).
3. Как запускать: кнопкой в приложении, по пресету, по расписанию (`dawg-replay schedule add` или блок «Регулярный запуск»). Нужен ли человек посреди запуска (код из SMS, подтверждение): по расписанию на такой вопрос может некому ответить, договорись, что делать.
4. Что получить на выходе: файл (CSV, Excel, JSON), таблица на экране запуска, скриншоты как доказательство (`artifact` с `image/png`, видны миниатюрой), PDF, ссылки (например, на таблицу клиента), итог одной строкой с числом (`kit.result(..., count=..., main=...)`). У приложения есть свои уведомления в Telegram (Настройки, блок Telegram): об итоге, падении и вопросе скрипта, с правилами у скрипта и расписания, ответ на `kit.ask` прямо из чата. Чтобы итог пришёл в личку, скрипту ничего слать не нужно; на «присылай мне в Telegram» предложи подключить бота в Настройках. Почту, вебхук, Google Sheets, групповой чат или особый формат сообщения скрипт может сделать сам: токен бота, пароль почты или ключ сервиса приходят параметром `secret` (ключ сервиса файлом `file` с `secret = true`), адрес или id чата обычным параметром.

Скрипт это обычная программа на Python: если у сайта или сервиса клиента есть API (поиск отдаёт JSON, у сервиса есть REST), надёжнее звать его прямо из скрипта, без браузера; браузер DAWG нужен там, где без него сайт не отдаёт данные или не даёт действовать. Задача вообще без сайта (обработать файл клиента, сходить в его API) тоже годится: браузер в таком скрипте не открывается, `dawg-mcp` для разведки не нужен.

Затем спроектируй параметры под ответы и покажи клиенту одной таблицей: поле, что в нём, тип, значение по умолчанию. Например: «Склады: несколько из списка (Москва, Казань), по умолчанию Москва; За какой день: вчера, при каждом запуске своё». Возражений нет: собирай.

## A. Новый скрипт

1. Разговор по разделу 1, затем коротко о сборе: что собрать и откуда, какие поля, что считать единицей прогресса (страница, карточка), примерный объём, куда отдавать данные (CSV по умолчанию; внешний сервис означает параметр `secret`). На «каждый день» скажи, что после регистрации клиент сохранит пресет и включит регулярный запуск на странице скрипта (или `dawg-replay schedule add`).
2. Разведка по [exploration.md](exploration.md). Пройди весь путь на 1-2 реальных примерах. Сначала ищи внутренний JSON-API в сетевых ответах и данные в странице (`__NEXT_DATA__`, `data-state` и подобное), DOM только если их нет. Выясни пагинацию, ленивую подгрузку, какие проверки показывает сайт, нужен ли `geo` или прокси. Запиши находки: эндпоинты, параметры запросов, селекторы, особенности.
3. Сразу после разведки освободи браузер: `browser_release` (и проверь `browser_list_sessions`). Код пишешь без открытого браузера: он тратит минуты клиента. Понадобилось уточнить: открой новый, уточни, освободи.
4. Сборка на основе [template.py](template.py) по [contract.md](contract.md): `contract = "1.3"`, как в шаблоне (возможности ниже требуют 1.3, `"1.1"` оставляй только скрипту без них), `site` (как сайт называет клиент: «Ozon», «Яндекс Маркет») и `tags` (1-3 метки о том, что собирается: «Цены», «Отзывы»), по ним клиент находит скрипт в библиотеке; всё изменяемое в параметрах манифеста (варианты с понятными подписями `{ value, title }`, несколько вариантов сразу `multi_enum`, у регулярного отчёта дата относительная: `default = "today-1"` или `"prev_month_start"`; документ, картинку или архив на входе даёт параметр `file` с `accept` и `max_mb`, ключ или сертификат сервиса `file` с `secret = true`, скрипт читает файл по `kit.params.<имя>["path"]`; контракт 1.3), браузер только через `kit.browser()` и `kit.set_browser_limit(n)`, повторы с паузами и таймауты, `kit.progress`, `kit.metric`, `kit.rows`, файл через `kit.artifact` (скриншот как доказательство действия с `mime` `image/png`, его видно на экране запуска), в конце `kit.result` с `count` (сколько собрано) и, если файлов несколько, `main` (главный). Если результат пойдёт на вход другому скрипту (раздел E), объяви файлы в `[[outputs]]` с `columns` и поставь `contract = "1.4"`. Собранное пишется в файл по ходу работы; падение на середине даёт `result: partial`. В шапке комментарий: откуда данные, что нашла разведка, дата. Файл: `./<name>/script.py`.
5. Проверка:
   - `dawg-replay validate <name>/script.py`;
   - `dawg-replay run <name>/script.py --set <параметр объёма>=1 --set ... --json --follow` (например `max_pages=1`): самый маленький прогон; в ответе `run.id`, `run.status`, `run_dir`;
   - `dawg-replay logs <run_id> --events` и файлы в `<run_dir>/output/`: открой CSV и сверь 3 строки с сайтом. Код выхода 0 и `ok` ничего не доказывают: проверяешь данные;
   - не сошлось: правь и повторяй. Затем пройди [checklist.md](checklist.md).
6. Регистрация: `dawg-replay add <name>/script.py`. Скажи клиенту простыми словами: `dawg-replay ui` откроет приложение в браузере, на экране «Скрипты» его скрипт, на экране скрипта форма; что значит каждый параметр, сколько примерно идёт запуск, где скачать результат, что делать, если сайт сменится (прийти к тебе с фразой «скрипт сломался»). Скажи и про черновик: приложение хранит свою копию, файл `./<name>/script.py` (назови полный путь) можно удалить или оставить для следующей правки.

## B. Действия на сайте по таблице

Клиент даёт список (Excel, CSV, TSV или JSON), и для каждой строки скрипт делает одно и то же на сайте: входит в аккаунт, меняет цену или настройку, отправляет форму, проверяет статус. Основа: [template_actions.py](template_actions.py).

1. Разговор по разделу 1, затем о действиях. Узнай: что сделать для одной строки и как сайт показывает, что получилось; какие колонки будут в таблице (они станут `columns` параметра `table`); нужен ли вход и чей это кабинет (только кабинеты самого клиента или те, на которые у него есть право); спрашивает ли сайт код из SMS или письма; что делать, если строка не прошла (по умолчанию остальные строки продолжаются). Спроси, как будут приходить входные данные, и назови все три способа: новый файл Excel, CSV, TSV или JSON на каждый запуск; таблица, сохранённая в пресете, для регулярного запуска по расписанию; одна-две строки, введённые руками в форме запуска («Ввести вручную») или в терминале (`--row`), когда нужно сделать что-то для одного аккаунта. Обычно один параметр `table` с нужными `columns` годится для всех трёх, отдельные параметры под каждый способ не нужны. Таблица с `secret = true` тоже сохраняется в пресет (отдельным файлом, только у клиента на компьютере), так что регулярный запуск по ней работает; таблица, загруженная или введённая в форму, заменяет таблицу пресета только в этом запуске. Попроси у клиента таблицу на 1-2 строки для разведки.
2. Разведка действий по [exploration.md](exploration.md), раздел «Действия». Путь проходится на одной строке. Перед первым действием, которое что-то меняет на сайте (сохранить, отправить, оплатить, удалить), остановись и спроси клиента в чате, можно ли; без ответа «да» не нажимай. Запиши: как понять, что вход выполнен; где видно, что действие уже сделано; признак успеха после действия; сообщения сайта об ошибках. Освободи браузер.
3. Сборка на основе [template_actions.py](template_actions.py) по [contract.md](contract.md):
   - вход: параметр `table` с колонками логина и пароля и `secret = true`, или параметры `secret`, если аккаунт один; пароли и коды в коде, `default` и событиях не появляются;
   - `columns` перечисляют все колонки, без которых строку не сделать: по ним форма строит таблицу для ввода руками и проверяет загруженный файл, пустое значение такой колонки в любой строке даёт ошибку до запуска; необязательные колонки (комментарий) в `columns` не включай; при `contract = "1.3"` объяви и остальное, что договорено с клиентом: `input` (только те способы ввода, которые клиенту нужны, например `["file", "preset"]` для выгрузки из его системы по расписанию), `sheet`, если в книге Excel нужен не первый лист, `column_types` для чисел, дат и да/нет, чтобы скрипт получал готовые значения, а ошибки в файле были видны до запуска; названия колонок короткие и понятные клиенту (`email`, `password`, `price`), такие же, как в его файле;
   - `kit.browser(login=...)` сохраняет вход между запусками, скрипт сам проверяет, вошёл ли он, и входит заново, если сайт отозвал сессию; сразу после успешного входа `b.save_login()`: только так появляется новый вход (без этого вызова kit его не сохранит), и он не потеряется при обрыве запуска;
   - код из SMS или письма спрашивается у человека: `kit.ask(..., secret=True)` (контракт, раздел 8); перед первым изменением на сайте `kit.ask(..., kind="confirm")`, если клиент не отказался от подтверждения;
   - перед действием проверка, не сделано ли оно уже: повторный запуск и «Перезапустить упавшие» не создают дублей;
   - каждая строка в своём `try`: упавшая не останавливает остальные; итог строки `kit.item(key, "ok" | "failed" | "skipped", msg, row=row["_row"])`; у секретной таблицы ключ это номер строки, а не логин (значения секретной таблицы в событиях маскируются);
   - отчёт по строкам и его CSV приложение строит из `kit.item`, свой `report.csv` не пиши; в конце `kit.result`: `ok`, `partial`, если часть строк упала, `failed`, если упали все.
4. Проверка: `dawg-replay validate`, затем запуск на таблице из одной строки с `check_only=true` (ничего не меняет), затем, с согласия клиента, на одной строке по-настоящему и ещё раз на той же строке: второй запуск должен дать `skipped` «уже сделано». Строку с заведомо неверными данными проверь отдельно: она `failed` с понятным сообщением, остальные строки идут дальше. Затем [checklist.md](checklist.md), раздел «Действия».
5. Регистрация и рассказ клиенту, как в A.6, плюс: как передать строки, все три способа: загрузить файл в форму запуска, ввести одну-несколько строк в форме («Ввести вручную») или в терминале (`dawg-replay run <скрипт> --row accounts email=… password=-`, где `-` спросит пароль скрыто), сохранить таблицу в пресет для регулярного запуска (секретную тоже, её содержимое видно только на этом компьютере); сохранённые входы видны на странице скрипта, «Забыть» стирает вход; вопрос с кодом появляется на экране запуска; «Перезапустить упавшие» повторяет только упавшие строки.

## D. Одно действие или проверка страницы

Без таблицы: «посмотри цену и пришли скриншот», «если статус сменился, нажми кнопку», «отправь одну заявку с этим документом». Основа: [template_task.py](template_task.py).

1. Разговор по разделу 1, затем: какая страница (адрес как параметр `url` или выбор из вариантов), что на ней читать, при каком условии действовать, что считать доказательством (обычно скриншот до и после).
2. Разведка по [exploration.md](exploration.md): где значение, как сайт показывает, что действие уже сделано, признак успеха. Перед первым действием, которое что-то меняет, спроси клиента в чате.
3. Сборка на основе [template_task.py](template_task.py): режим `enum` с подписями «только проверить» и «проверить и сделать», условие параметром, дата «за вчера» относительная, файл для формы параметром `file`; перед действием проверка «уже сделано» и `kit.ask(..., kind="confirm")`; скриншоты через `kit.artifact(..., "image/png")`; в конце `kit.result` с `count` (сколько значений прочитано), `main` (главный скриншот или файл) и `links` (страница).
4. Проверка: `dawg-replay validate`, запуск в режиме «только проверить», открыть скриншот на экране запуска и сверить значение со страницей; затем, с согласия клиента, один настоящий запуск и повторный: второй не должен повторить действие. Затем [checklist.md](checklist.md).
5. Регистрация и рассказ клиенту, как в A.6: где скриншот (миниатюра на экране запуска), как поставить проверку по расписанию.

## E. Цепочка скриптов: связи

Результат одного скрипта идёт на вход другому: «цены WB и цены Ozon, потом обновить мои цены, потом отчёт». Приложение соединяет скрипты связями: получатель запускается после источника и/или получает файл его результата в параметр `table` или `file`. Связи видны и правятся на экране «Связи» в приложении. Один скрипт-оркестратор, который сам вызывает другие, не пиши, если клиент об этом не попросил: такую схему клиент не видит, у неё нет своих расписаний и уведомлений по шагам.

1. Разговор. Нарисуй клиенту схему словами: какие скрипты, что из чего берёт, кто кого запускает. Для каждой связи договорись:
   - когда запускать получателя: после успешного (по умолчанию), после успешного или частичного, после любого исхода, или не запускать, а только брать последний результат источника, когда получатель запускается сам (по расписанию или кнопкой);
   - какие файлы передать в какие параметры;
   - у получателя с несколькими источниками: ждать всех (по умолчанию, со сроком ожидания отстающего, 6 часов, и что делать по сроку: пропустить или запустить с тем, что есть) или запускать после каждого;
   - расписание обычно нужно только первым скриптам цепочки, остальные идут по связям.
2. Каждый скрипт собирается и проверяется сам по себе по разделу A, B или D. У источника объяви выходы в манифесте (`[[outputs]]`, контракт, раздел 4.3) с `columns` таблиц и `contract = "1.4"`. Файл, который скрипт отдаёт не в каждом запуске (нет подходящих строк, ветка «да» или «нет»), объяви с `optional = true`: иначе его отсутствие считается тихой поломкой. У получателя параметр `table` с теми же названиями колонок в `columns`: несовпадение колонок не даст получателю стартовать. Параметр, который приходит по связи, клиенту руками заполнять не нужно; `input` у него оставь как договорились для ручного запуска.
3. После `dawg-replay add` всех скриптов собери связи:
   - `dawg-replay link add <источник> <получатель> --file prices.csv=<параметр>` (файл по имени, шаблону `prices-*.csv` или `@main` для главного файла; `--after ok|partial|any|never`, `--preset <пресет получателя>`);
   - `dawg-replay link mode <получатель> all --wait 6h --on-timeout skip` для нескольких источников;
   - круг (А запускает Б, Б запускает А) сохраняется только с пределом на одной из связей: `--limit-per-day N`.
4. Проверка: `dawg-replay link check`. Ошибки (круг без предела, параметр не того типа, секретный параметр) исправь; предупреждения (нет колонки, нужной получателю) прочитай: код выхода при них 0. Затем прогон: запусти источник маленьким прогоном (`--follow`), убедись, что получатель запустился по связи (`dawg-replay runs <получатель>`, пометка «[по связи после <источник>]») и получил файл, и сверь его результат. Разовую передачу без связи проверяют ссылкой на результат: `dawg-replay run <получатель> --set <параметр>=last:<источник>:prices.csv --follow`. Почему получатель не запустился, видно в `dawg-replay link show <источник> <получатель>`.
5. Скажи клиенту: откройте экран «Связи» в приложении (`dawg-replay ui`), там вся схема; стрелку можно протянуть мышкой от кружка справа у скрипта, клик по подписи стрелки открывает настройки связи и её последние решения, по скрипту его режим ожидания; на странице каждого скрипта блок «Откуда берёт данные» и «Что запускает после». На экране запуска видно, после чего он запущен и какие файлы получил; «Передать в другой скрипт» передаёт файлы разово.

## C. Скрипт сломался

1. `dawg-replay runs <name> --json`: найди упавший запуск.
2. `dawg-replay logs <run_id> --events` (и без `--events` для stderr): где именно и почему.
3. Пройди это место заново через `dawg-mcp`, затем `browser_release`.
4. Возьми текущую версию: `dawg-replay show <name> --json`, поле `path`. Скопируй этот файл в `./<name>/script.py`. Если там уже лежит старый черновик, сначала сравни его с текущей версией (`diff`): отличия в черновике могут быть чьими-то правками, которые не попали в приложение; покажи их клиенту и спроси, переносить ли. Молча черновик не перезаписывай.
5. Правь `./<name>/script.py`, подними `version` на 1; у скрипта с `contract = 1` поставь `contract = "1.1"` и заполни `site` и `tags`, если их нет, и `dawg-replay-kit>=1.1,<2` в зависимостях; проверь по шагу A.5 и [checklist.md](checklist.md), `dawg-replay add`.
6. Новый скрипт с нуля только если клиент сам попросил.

Причина не в коде (кончились минуты, неверный ключ, лимит браузеров тарифа, сайт не пропустил браузер через свою проверку): скажи клиенту как есть и предложи запустить позже, с другим `geo` или взять другой источник. Скрипт ради этого не правь.

## Красные флаги: остановись

- В коде строка, которую ты скопировал из адресной строки или из ответа сервера во время разведки.
- «Сейчас быстро допишу, браузер пока пусть висит».
- «Проверка сайта висит, нажму сам».
- «Запуск `ok`, значит работает» без открытого CSV.
- «Нажму „Сохранить“ на разведке, это же тестовые данные» без ответа клиента.
- Действие без проверки «уже сделано»: второй запуск сделает его ещё раз.
- «Свяжу скрипты, `link check` без ошибок, значит работает» без прогона источника и проверки, что получатель запустился и получил файл.
