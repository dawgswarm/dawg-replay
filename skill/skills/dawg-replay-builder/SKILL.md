# dawg-replay-builder

Ты один раз проходишь путь по сайту через браузер DAWG (`dawg-mcp`) и превращаешь его в скрипт `script.py` по контракту `dawg-replay`. Дальше скрипт работает без тебя: клиент запускает его в приложении, меняет параметры и платит только минутами DAWG.

Скрипт либо собирает данные (раздел A), либо делает действия на сайте по строкам таблицы клиента (раздел B): входит в его кабинет, заполняет формы, меняет настройки, проверяет статусы.

Справочные файлы рядом:

| Файл | Когда читать |
|---|---|
| [contract.md](contract.md) | форма скрипта, типы параметров, события, браузеры; перед сборкой |
| [exploration.md](exploration.md) | как разведывать сайт через `dawg-mcp`; перед разведкой |
| [template.py](template.py) | эталонный скрипт сбора данных; основа для раздела A |
| [template_actions.py](template_actions.py) | эталонный скрипт действий по таблице; основа для раздела B |
| [checklist.md](checklist.md) | проверки перед `dawg-replay add`; обязательно |

## 0. Проверка окружения (всегда первым шагом)

1. Инструменты браузера DAWG: среди твоих инструментов есть `browser_provision`, `browser_navigate`, `browser_snapshot`, `browser_release` с любым префиксом сервера (`mcp__dawg__browser_provision`, `mcp__plugin_..._dawg__browser_provision` и так далее). Нет таких инструментов: `dawg-mcp` не подключён.
2. Приложение: `dawg-replay --version --json`. В `contract_versions` должна быть `1.2`. Команда не найдена, поля нет или там другая версия: приложение не установлено или старое (`uv tool upgrade dawg-replay`).
3. Ключ: `dawg-replay --json config show`, поле `api_key_set`. `false`: попроси клиента выполнить `dawg-replay config set-key` (или ввести ключ в UI на экране Настройки). Ключ сам не вводи и не проси прислать его в чат.

Если 1 или 2 не выполнены, объясни клиенту, что поставить, и дальше не иди:

- `dawg-replay`: `uv tool install dawg-replay`, нужен `uv` (https://docs.astral.sh/uv/) и Python 3.10+.
- `dawg-mcp` в Claude Code: плагин `dawg-replay-builder` подключает его сам; вручную `claude mcp add dawg --scope user --env DAWG_API_KEY=<ключ> -- uvx --with 'mcp<2' dawg-mcp`. В Codex: блок `[mcp_servers.dawg]` в `~/.codex/config.toml` (см. README плагина). После подключения перезапусти сессию.

## Черновики: каждый скрипт в своей папке

Сессия может работать над несколькими скриптами, поэтому черновик каждого лежит отдельно: `./<name>/script.py`, где `<name>` это `name` из манифеста (slug, например `ozon-prices`). Рядом можно класть заметки разведки. Все команды `validate`, `run`, `add` получают путь `<name>/script.py`.

- Перед записью проверь папку. Её нет: создай. В ней `script.py` с другим `name` в манифесте: это чужой черновик, спроси клиента или возьми другое `name`.
- Приложение при `add` хранит свою копию, черновик ему потом не нужен.

## A. Новый скрипт

1. Разговор, коротко. Узнай: что собрать и откуда, какие поля, что клиент будет менять между запусками (это параметры), что считать единицей прогресса (страница, карточка), примерный объём, куда отдавать данные (CSV по умолчанию; внешний сервис означает параметр `secret`). Не больше 2-3 вопросов за раз; очевидное выбери сам и скажи, что выбрал. На «каждый день» скажи, что после регистрации клиент сохранит пресет и включит регулярный запуск на странице скрипта (или `dawg-replay schedule add`).
2. Разведка по [exploration.md](exploration.md). Пройди весь путь на 1-2 реальных примерах. Сначала ищи внутренний JSON-API в сетевых ответах и данные в странице (`__NEXT_DATA__`, `data-state` и подобное), DOM только если их нет. Выясни пагинацию, ленивую подгрузку, какие проверки показывает сайт, нужен ли `geo` или прокси. Запиши находки: эндпоинты, параметры запросов, селекторы, особенности.
3. Сразу после разведки освободи браузер: `browser_release` (и проверь `browser_list_sessions`). Код пишешь без открытого браузера: он тратит минуты клиента. Понадобилось уточнить: открой новый, уточни, освободи.
4. Сборка на основе [template.py](template.py) по [contract.md](contract.md): `contract = "1.1"`, `site` (как сайт называет клиент: «Ozon», «Яндекс Маркет») и `tags` (1-3 метки о том, что собирается: «Цены», «Отзывы»), по ним клиент находит скрипт в библиотеке; всё изменяемое в параметрах манифеста, браузер только через `kit.browser()` и `kit.set_browser_limit(n)`, повторы с паузами и таймауты, `kit.progress`, `kit.metric`, `kit.rows`, файл через `kit.artifact` (скриншот как доказательство действия с `mime` `image/png`, его видно на экране запуска), в конце `kit.result` с `count` (сколько собрано) и, если файлов несколько, `main` (главный). Собранное пишется в файл по ходу работы; падение на середине даёт `result: partial`. В шапке комментарий: откуда данные, что нашла разведка, дата. Файл: `./<name>/script.py`.
5. Проверка:
   - `dawg-replay validate <name>/script.py`;
   - `dawg-replay run <name>/script.py --set <параметр объёма>=1 --set ... --json --follow` (например `max_pages=1`): самый маленький прогон; в ответе `run.id`, `run.status`, `run_dir`;
   - `dawg-replay logs <run_id> --events` и файлы в `<run_dir>/output/`: открой CSV и сверь 3 строки с сайтом. Код выхода 0 и `ok` ничего не доказывают: проверяешь данные;
   - не сошлось: правь и повторяй. Затем пройди [checklist.md](checklist.md).
6. Регистрация: `dawg-replay add <name>/script.py`. Скажи клиенту простыми словами: `dawg-replay ui` откроет приложение в браузере, на экране «Скрипты» его скрипт, на экране скрипта форма; что значит каждый параметр, сколько примерно идёт запуск, где скачать результат, что делать, если сайт сменится (прийти к тебе с фразой «скрипт сломался»). Скажи и про черновик: приложение хранит свою копию, файл `./<name>/script.py` (назови полный путь) можно удалить или оставить для следующей правки.

## B. Действия на сайте по таблице

Клиент даёт список (Excel или CSV), и для каждой строки скрипт делает одно и то же на сайте: входит в аккаунт, меняет цену или настройку, отправляет форму, проверяет статус. Основа: [template_actions.py](template_actions.py).

1. Разговор. Узнай: что сделать для одной строки и как сайт показывает, что получилось; какие колонки будут в таблице (они станут `columns` параметра `table`); нужен ли вход и чей это кабинет (только кабинеты самого клиента или те, на которые у него есть право); спрашивает ли сайт код из SMS или письма; что делать, если строка не прошла (по умолчанию остальные строки продолжаются). Спроси, как будут приходить входные данные, и назови все три способа: новый файл Excel или CSV на каждый запуск; таблица, сохранённая в пресете, для регулярного запуска по расписанию; одна-две строки, введённые руками в форме запуска («Ввести вручную») или в терминале (`--row`), когда нужно сделать что-то для одного аккаунта. Обычно один параметр `table` с нужными `columns` годится для всех трёх, отдельные параметры под каждый способ не нужны. Таблица с `secret = true` тоже сохраняется в пресет (отдельным файлом, только у клиента на компьютере), так что регулярный запуск по ней работает; таблица, загруженная или введённая в форму, заменяет таблицу пресета только в этом запуске. Попроси у клиента таблицу на 1-2 строки для разведки.
2. Разведка действий по [exploration.md](exploration.md), раздел «Действия». Путь проходится на одной строке. Перед первым действием, которое что-то меняет на сайте (сохранить, отправить, оплатить, удалить), остановись и спроси клиента в чате, можно ли; без ответа «да» не нажимай. Запиши: как понять, что вход выполнен; где видно, что действие уже сделано; признак успеха после действия; сообщения сайта об ошибках. Освободи браузер.
3. Сборка на основе [template_actions.py](template_actions.py) по [contract.md](contract.md):
   - вход: параметр `table` с колонками логина и пароля и `secret = true`, или параметры `secret`, если аккаунт один; пароли и коды в коде, `default` и событиях не появляются;
   - `columns` перечисляют все колонки, без которых строку не сделать: по ним форма строит таблицу для ввода руками и проверяет загруженный файл, пустое значение такой колонки в любой строке даёт ошибку до запуска; необязательные колонки (комментарий) в `columns` не включай; названия колонок короткие и понятные клиенту (`email`, `password`, `price`), такие же, как в его файле;
   - `kit.browser(login=...)` сохраняет вход между запусками, скрипт сам проверяет, вошёл ли он, и входит заново, если сайт отозвал сессию; сразу после успешного входа `b.save_login()`: только так появляется новый вход (без этого вызова kit его не сохранит), и он не потеряется при обрыве запуска;
   - код из SMS или письма спрашивается у человека: `kit.ask(..., secret=True)` (контракт, раздел 8); перед первым изменением на сайте `kit.ask(..., kind="confirm")`, если клиент не отказался от подтверждения;
   - перед действием проверка, не сделано ли оно уже: повторный запуск и «Перезапустить упавшие» не создают дублей;
   - каждая строка в своём `try`: упавшая не останавливает остальные; итог строки `kit.item(key, "ok" | "failed" | "skipped", msg, row=row["_row"])`; у секретной таблицы ключ это номер строки, а не логин (значения секретной таблицы в событиях маскируются);
   - отчёт по строкам и его CSV приложение строит из `kit.item`, свой `report.csv` не пиши; в конце `kit.result`: `ok`, `partial`, если часть строк упала, `failed`, если упали все.
4. Проверка: `dawg-replay validate`, затем запуск на таблице из одной строки с `check_only=true` (ничего не меняет), затем, с согласия клиента, на одной строке по-настоящему и ещё раз на той же строке: второй запуск должен дать `skipped` «уже сделано». Строку с заведомо неверными данными проверь отдельно: она `failed` с понятным сообщением, остальные строки идут дальше. Затем [checklist.md](checklist.md), раздел «Действия».
5. Регистрация и рассказ клиенту, как в A.6, плюс: как передать строки, все три способа: загрузить файл в форму запуска, ввести одну-несколько строк в форме («Ввести вручную») или в терминале (`dawg-replay run <скрипт> --row accounts email=… password=-`, где `-` спросит пароль скрыто), сохранить таблицу в пресет для регулярного запуска (секретную тоже, её содержимое видно только на этом компьютере); сохранённые входы видны на странице скрипта, «Забыть» стирает вход; вопрос с кодом появляется на экране запуска; «Перезапустить упавшие» повторяет только упавшие строки.

## C. Скрипт сломался

1. `dawg-replay runs <name> --json`: найди упавший запуск.
2. `dawg-replay logs <run_id> --events` (и без `--events` для stderr): где именно и почему.
3. Пройди это место заново через `dawg-mcp`, затем `browser_release`.
4. Возьми текущую версию: `dawg-replay show <name> --json`, поле `path`. Скопируй этот файл в `./<name>/script.py`. Если там уже лежит старый черновик, сначала сравни его с текущей версией (`diff`): отличия в черновике могут быть чьими-то правками, которые не попали в приложение; покажи их клиенту и спроси, переносить ли. Молча черновик не перезаписывай.
5. Правь `./<name>/script.py`, подними `version` на 1; у скрипта с `contract = 1` поставь `contract = "1.1"` и заполни `site` и `tags`, если их нет, и `dawg-replay-kit>=1.1,<2` в зависимостях; проверь по шагу A.5 и [checklist.md](checklist.md), `dawg-replay add`.
6. Новый скрипт с нуля только если клиент сам попросил.

Причина не в коде (кончились минуты, неверный ключ, лимит браузеров тарифа, сайт не пропустил браузер через свою проверку): скажи клиенту как есть и предложи запустить позже, с другим `geo` или взять другой источник. Скрипт ради этого не правь.

## Запреты

| Нельзя | Почему | Как надо |
|---|---|---|
| Оставлять в коде значения из разведки: запрос, город, id категории, конкретные URL с параметрами поиска, cookies, токены из сетевых ответов | скрипт работает только для того примера, клиент не может ничего поменять | параметр манифеста с `default`; токены и cookies скрипт получает сам при каждом запуске |
| Зависеть от сессии MCP: `session_id`, CDP-адрес, открытая вкладка, ручной шаг агента | после твоего ухода скрипт падает | скрипт сам открывает браузер через `kit.browser()` |
| Что-то делать с проверкой сайта самому: кликать, вводить, менять заголовки | проверки сайта браузер DAWG проходит сам, вмешательство только мешает | ждать по признаку на странице с разумным таймаутом; не прошла: в скрипте понятная ошибка, клиенту сказать как есть |
| Держать браузер `dawg-mcp` открытым после разведки | клиент платит за минуты простоя | `browser_release` сразу после разведки |
| Считать скрипт готовым по коду выхода 0 | пустые или чужие данные тоже дают 0 | сверить строки CSV с сайтом |
| Писать новый скрипт вместо починки | теряются версии и пресеты клиента | тот же `name`, `version + 1` |
| Нажимать на разведке то, что меняет данные на сайте, без «да» клиента | изменение на сайте не отменить | спросить в чате перед первым таким действием |
| Пароли, коды, токены в коде, `default`, параметрах `string` или ключах `kit.item` | они попадают в историю, пресеты и логи | таблица с `secret = true`, параметры `secret`, `kit.ask(..., secret=True)` |
| Обходить или трогать проверки сайта, маскировать автоматизацию, подделывать отпечатки | это против правил сайта; браузер DAWG проходит проверки сам | ждать признак на странице; не прошло: понятная ошибка клиенту |
| Действовать в чужих аккаунтах или там, куда у клиента нет права | скрипт действует от имени клиента, отвечает за это он | только кабинеты клиента и те, где у него есть право; сомнение: спросить |

## Красные флаги: остановись

- В коде строка, которую ты скопировал из адресной строки или из ответа сервера во время разведки.
- «Сейчас быстро допишу, браузер пока пусть висит».
- «Проверка сайта висит, нажму сам».
- «Запуск `ok`, значит работает» без открытого CSV.
- «Нажму „Сохранить“ на разведке, это же тестовые данные» без ответа клиента.
- Действие без проверки «уже сделано»: второй запуск сделает его ещё раз.
