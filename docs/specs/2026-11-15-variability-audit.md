# Аудит вариативности (dr-78)

Принцип: dawg-replay и скилл для автоматизаций любого характера. Приложение ничего не навязывает, скрипт через контракт объявляет, что ему нужно, агент договаривается с клиентом. Брейншторм команды: dev1 (вход), dev2 (выход), dev3 (запуск и скилл). Всё ниже аддитивно: контракт 1.3, старые скрипты работают без изменений.

## Вход и параметры

| Что | Зачем клиенту | Цена |
|---|---|---|
| Тип `file`: картинка, PDF, архив, любой файл; секретный файл (ключ сервиса) | фото товаров на маркетплейс, PDF счетов в кабинет, выгрузка в Google Sheets по сервисному ключу | M-L |
| Относительные даты: `default = "today-1"`, «начало месяца» | ежедневный отчёт «за вчера» по расписанию | M |
| Подписи у `enum`, `multi_enum`, `time`/`datetime` | выбрать склады, категории; в форме «дешевле», а не `price` | S |
| Способы ввода таблицы объявляет скрипт (`input = [file, manual, preset]`), выбор листа XLSX, типы колонок | скрипт решает сам, приложение не навязывает (Q27) | M |
| Данные из другого запуска: результат как вход | собрать заказы, потом по ним действовать | L |
| «Спросить при запуске»: пустое значение пресета | расписание с одним меняющимся полем | M |

## Запуск и оркестрация

| Что | Зачем клиенту | Цена |
|---|---|---|
| Запуск по ссылке (вебхук) | дёрнуть из 1С, CRM, n8n, когда пришёл заказ | M (служба вместо `dawg-replay ui`: L) |
| Запуск по файлу в папке | бросил выгрузку в папку, обработалось | M |
| Цепочки: «после ok запустить Б», файл результата в параметр Б | сбор цен, потом обновление своих цен | M |
| Разбить большую таблицу на N параллельных запусков | 1000+ строк за часы | M |
| Перезапуск упавших при нескольких таблицах | аккаунты × товары | S-M, нужно редко |

## Выход и доставка

| Что | Зачем клиенту | Цена |
|---|---|---|
| Уведомления: Telegram и вебхук на итог, падение, вопрос | без этого расписание с вопросом почти всегда даёт таймаут | M |
| Ответ на вопрос прямо из Telegram | код из SMS, когда клиент не у компьютера | M сверху |
| Превью картинок и PDF на экране запуска | скриншот как доказательство «заявка отправлена» | S |
| Zip всех файлов, история запусков в CSV, отчёт по строкам в xlsx | отдать результат одним файлом | S |
| «Что изменилось с прошлого запуска», история значения по ключу (dr-51) | мониторинг цен | L |
| `result.count`, ссылки и главный файл в итоге | точная тихая поломка, понятный итог | S |
| Лимиты (журнал 2000, загрузка 10 МБ) в настройки | большие задачи | S |

## Скилл

| Что | Зачем | Цена |
|---|---|---|
| Разговор начинается с «как удобно давать данные, запускать, получать итог» и подстраивает скрипт | главное сужение сейчас: два пути, сбор и действия | S |
| Третий шаблон: сценарий без таблицы (одно действие, мониторинг) | не всё ложится в «по строкам» | S |

## Не делаем сейчас

Превью html (риск XSS ради редкого случая), почта (вебхук покрывает через интеграции), Google Sheets внутри приложения (делает скрипт), json-параметры, общие наборы на несколько скриптов, подъём лимитов самим скриптом.

## Предложение по этапам

1. **M4 «Гибкость без инфраструктуры»** (S-M каждое, параллельно): скилл (разговор и третий шаблон), `enum` с подписями, `multi_enum`, `time`/`datetime`, относительные даты, `input` у таблицы, тип `file` и секретный файл, превью картинок и PDF, zip, `result.count`.
2. **M5 «Связь с миром»**: уведомления Telegram и вебхук, ответ на вопрос из Telegram, запуск по ссылке и по папке, фоновая служба.
3. **M6 «Данные между запусками»**: цепочки, результат как вход, «что изменилось» (dr-51), шарды больших таблиц.
