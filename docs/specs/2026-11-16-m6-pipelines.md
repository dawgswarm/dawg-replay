# M6: результат одного скрипта как вход другого (связи и пайплайны)

## Зачем

Сейчас каждый скрипт живёт сам по себе. Пользователь, у которого «собрать цены WB» и «собрать цены Ozon» складывают файлы, а «обновить мои цены» их читает, вручную скачивает результат и загружает в другой скрипт, а время запусков подбирает на глаз. Нужно, чтобы результат одного запуска шёл на вход другому, а запуски шли друг за другом сами.

Какими будут пайплайны, заранее неизвестно: от пары скриптов до сложных схем с ветвлениями и слияниями. Поэтому приложение даёт простые строительные блоки, а схему под задачу собирает агент в разговоре с пользователем (скилл). Пользователь видит итог схемой и может сам её править.

## Цели

- Связь между двумя скриптами: «запускать после» с условием и/или «передать файл результата в параметр».
- Ссылка на результат другого запуска как источник значения параметра: конкретный запуск или «последний успешный результат скрипта X, файл Y». Её можно сохранить в пресете и расписании.
- Схема всех связей на новом экране «Связи», которую можно править мышкой, и блок связей на странице каждого скрипта.
- Кнопка «Передать в другой скрипт» на экране запуска для разовой ручной передачи.
- Команды CLI, которыми агент собирает и проверяет пайплайн без UI.
- Скилл учит агента выяснять, нужен один скрипт или цепочка, и собирать цепочку из этих блоков.

## Не цели

- Свой язык описания пайплайнов, условия по содержимому результата («запустить, если строк больше 100»), ветвление по данным. Такую логику агент пишет внутри скрипта.
- Передача данных в памяти или потоком между одновременно идущими скриптами. Передаётся только готовый файл завершённого запуска.
- Пайплайн как отдельная сущность со своим запуском, версиями и экспортом. Пайплайн здесь это просто набор связей.
- Связи между разными установками приложения, вебхуки, запуск по ссылке (остаток M5).

## Анти-цели

- Пользователь не понимает, почему запустился или не запустился скрипт. У каждого запуска по связи видно, что его запустило и какие файлы он получил, а у пропущенного видно почему.
- Несовпадение колонок обнаруживается посреди ночного запуска. Оно показывается при сохранении связи (если выходы объявлены) и перед стартом запуска, понятной ошибкой.
- Бесконечный круг запусков.
- Связь без ведома пользователя тратит запуски: схема на экране «Связи» всегда показывает всё, что приложение запустит само.

## Подход

Выбран подход A: строительные блоки в самом приложении (связь, ссылка на результат, «запускать после»), схема собирается агентом и видна и правится на экране «Связи».

Отвергнуто:
- B. Агент пишет один скрипт-оркестратор, который сам вызывает другие. Гибко, но пайплайн не виден пользователю, им нельзя управлять без агента, расписания и уведомления работают только для оркестратора.
- C. Отдельная сущность «пайплайн» со своим редактором шагов. Тяжелее, жёстче, плохо подходит под простые случаи из двух скриптов и дублирует расписания.

Вид: вариант C из макетов. Общая карта на экране «Связи» для обзора и правки всего пайплайна, плюс блок на странице каждого скрипта со ссылкой «открыть на карте». Агент, собрав пайплайн, говорит пользователю: «посмотрите экран Связи».

## Связь

Связь соединяет скрипт-источник и скрипт-получатель. У неё есть:

- Запуск: «после успешного», «после успешного или частичного», «после любого исхода», «не запускать, только файл». Отмена пользователем ничего не запускает.
- Передача файлов, ноль или больше строк: «файл результата источника → параметр получателя». Параметр получателя типа `table` или `file`. Передача разрешена и в `table` без способа ввода `file` (файл подставляет приложение, а не пользователь). В секретные `table`/`file` передача не разрешена, это ошибка при сохранении связи. Файл задаётся именем (или шаблоном, например `prices-*.csv`) в каталоге результата, либо как «главный файл» (`main` из `kit.result`). Шаблон совпал с несколькими файлами: берётся самый новый, а для `file` с `multiple` передаются все. Главный файл не задан или файла нет: как отсутствие результата (ниже).
- Пресет получателя, с которым он запускается по этой связи. По умолчанию без пресета. Значения остальных параметров берутся из пресета и умолчаний манифеста, как у запуска по расписанию.
- Включена или выключена.

Связь «только файл» сама ничего не запускает. Получатель, запущенный по своему расписанию, вручную или по другой связи, берёт по ней последний подходящий результат источника. «Подходящий» определяется тем же условием: по умолчанию последний успешный, можно разрешить частичный.

Между одной парой скриптов одна связь, в ней может быть несколько передач файлов.

## Несколько источников

Если у получателя несколько связей с запуском, на самом получателе выбирается режим (видно на карте подписью у узла):

- «После всех» (по умолчанию). Получатель запускается один раз, когда все источники с запуском закончились с подходящим исходом после последнего запуска получателя по связям. Срок ожидания отстающего задаётся на получателе (по умолчанию 6 часов от завершения первого источника). Когда срок вышел: «запустить с тем, что есть» (по передачам «только файл»-логикой: последний подходящий результат) или «пропустить» (по умолчанию). Пропуск виден в журнале запусков как запись получателя с причиной (как сейчас у пропуска по расписанию: `failed` с `reason` = skipped) и даёт уведомление `failed`.
- «После любого». Получатель запускается после каждого подходящего завершения источника, с самыми свежими подходящими файлами всех источников на этот момент.

Если источник закончился неподходящим исходом (упал при условии «успешно»), в режиме «после всех» этот круг ждёт до срока, повторный успешный запуск источника в пределах срока засчитывается.

Круг считается от последнего запуска получателя по связям; его запуски по расписанию и вручную круг не сбрасывают (решение лида: у получателя с расписанием и связями оба повода живут независимо).

Если компьютер был выключен, когда вышел срок, при первом удобном случае срок обрабатывается как обычно: «пропустить» даёт пропуск, «запустить с тем, что есть» запускает с опозданием, в журнале запуска строка «срок ожидания вышел в <время>, запущен позже: компьютер был выключен».

## Что считается исходом источника

«Любой исход» это любое завершение запуска, который действительно шёл: `ok`, `partial`, `failed`, в том числе таймаут и потерянный (`lost`). Запуск, который не стартовал (`not_started`, `skipped`), и отмена пользователем поводом не являются. Поэтому `not_started` получателя дальше по цепочке ничего не запускает.

## След решений по связи

Чтобы не шуметь каждую ночь, запись в истории запусков и уведомление `failed` дают только два случая: пропуск по сроку «после всех» и `not_started` получателя (файлы не подошли, обязательного нет, сломанный скрипт). Остальные «незапуски» (источник закончился неподходящим исходом, повод слит с уже идущим запуском, связь выключена, исчерпан предел) пишутся в журнал связи: на панели связи на карте и в `link show` последние решения с временем и причиной, например «не запущен: Цены WB упал». Строка «не передал: …» добавляется и в журнал запуска источника.

## Получение файлов запуском

- Перед стартом приложение для каждой передачи находит запуск источника (тот, что вызвал запуск, или последний подходящий), копирует файл в каталог входа запуска получателя и подставляет как значение параметра. Для `table` файл проходит ту же проверку, что загруженный руками: колонки `columns`, типы, `max_rows`. Ошибка: запуск не стартует, статус `not_started`, причина вида «Цены WB, prices.csv: нет колонки `sku`, нужна параметру `товары`».
- Явно переданное значение (форма запуска, `--param`) побеждает передачу по связи. В форме запуска параметр, который придёт по связи, показан как «из результата Цены WB, последний успешный (вчера 03:12)» с возможностью заменить.
- В записи запуска сохраняется, откуда он запущен (связь, запуск-источник) и из каких запусков взяты файлы. На экране запуска строка «Запущен после: Цены WB, запуск от …» и ссылки на запуски-источники; на экране источника «Передал в: …».
- Если подходящего результата источника нет вообще, параметр считается незаполненным: обязательный даёт `not_started` с понятной причиной.
- «Запустить снова» и «Перезапустить упавшие» берут те же файлы из тех же запусков-источников, что исходный запуск (в записи запуска хранится снимок: какой запуск, какой файл), а не ищут последний результат заново. Если файл источника уже удалён очисткой, это `not_started` с причиной.

## Ссылка на результат как значение параметра

Отдельно от связей, параметр `table`/`file` в форме запуска, пресете и расписании может получить значение «результат другого скрипта»: конкретный запуск, или «последний успешный (или частичный) результат скрипта X, файл Y». Это то же самое, что передача по связи «только файл», но без связи на карте; на карте такие ссылки показываются пунктирной стрелкой, чтобы картина была полной. Связь и ссылка в пресете это два способа записать одно и то же, хранить можно по-разному, решает исполнитель, требование: карта показывает оба.

## Объявление выходов в контракте (необязательное)

Скрипт может объявить, какие файлы он отдаёт. Новый блок в манифесте, контракт 1.4:

```toml
[[outputs]]
name = "prices.csv"          # имя или шаблон файла в каталоге результата
title = "Цены"
columns = ["sku", "price"]   # необязательно, для таблиц
main = true                  # необязательно: это главный файл
```

- Если выходы объявлены, карта и настройки связи предлагают их до первого запуска, а несовпадение колонок с параметром получателя видно сразу при сохранении связи (предупреждение, сохранять можно).
- Без объявления приложение предлагает файлы последнего запуска источника и допускает ввод имени руками.
- После запуска приложение сверяет объявленное с реальным: объявленного файла нет, это строка в журнале и тихая поломка (`repair.suspicion`).
- kit: модель и проверка блока, версия контракта 1.4; старые скрипты без блока работают как раньше. Скилл: агент заполняет `outputs`, когда пишет скрипт, результат которого может пригодиться другим.

## Циклы и защита

- Круг (А запускает Б, Б запускает А) разрешён, только если на одной из связей круга задан предел, например «не больше N запусков по этой связи в сутки». Сутки календарные, по местному времени. Предел исчерпан: получатель не запускается, решение пишется в журнал связи (см. «След решений по связи»). Без предела связь, замыкающая круг, не сохраняется, ошибка называет круг.
- Независимо от циклов: один и тот же скрипт не запускается по связи, пока предыдущий его запуск по связи ещё идёт; новый повод запомнить и запустить после (не больше одного отложенного), остальные поводы слить.
- Запуски по связям подчиняются тем же `max_parallel_runs` и ожиданию слота, что плановые.
- Удалённый скрипт удаляет свои связи; скрипт с ошибкой манифеста оставляет связи на карте красными, запуск по ним даёт `not_started`.

## Как запускается получатель

Своего демона у приложения нет. Решение «запускать ли получателя» принимает процесс, который закрыл запуск источника (`launch.supervise`, `recover_lost` и т.п.), тем же путём, что плановый запуск (`spawn_supervisor`), после `store.finish` и рядом с уведомлением Telegram. Срок ожидания «после всех» тоже должен срабатывать без открытого UI. Механизм на выбор исполнителя (одноразовая запись в планировщике ОС, проверка при каждом завершении любого запуска и при старте UI, и т.п.), требование: срок срабатывает с опозданием не больше нескольких минут, а при выключенном компьютере срабатывает при первом удобном случае и не запускает получателя с устаревшим кругом без следа в журнале.

## Уведомления

Запуск по связи для правил Telegram считается плановым (`done_scheduled`). В сообщении строка «после: <источник>». Ключ правил на уровне связи не вводится; переопределение у скрипта-получателя, как сейчас (`telegram_rules`, уровень `script:`).

## Экран «Связи»

- Узлы: скрипты, у которых есть связи или ссылки (переключатель «показать все скрипты»). На узле: название, расписание (если есть), режим «после всех / после любого», последний статус и итог.
- Стрелки: сплошная для связи с запуском, пунктирная для «только файл» и ссылок из пресетов. Подпись: передачи (`prices.csv → товары`) или «только после».
- Правка мышкой: протянуть стрелку от узла к узлу создаёт связь и открывает её настройки; клик по стрелке открывает панель настроек (условие, передачи, пресет, вкл/выкл, удалить); клик по узлу открывает настройки получателя (режим, срок) и ссылку на страницу скрипта. Узлы можно двигать, раскладка запоминается.
- Ошибки видны на схеме: несовпадение колонок, отсутствующий параметр, связь на сломанный скрипт, круг без предела (нельзя сохранить).
- Макет: `.superpowers/brainstorm/.../pipeline-view.html`, вариант A.

## Блок на странице скрипта

Строка «откуда берёт данные → этот скрипт → что запускает после», с теми же настройками, «+ источник», «+ запускать после» и ссылкой «открыть на карте». Макет: вариант B там же.

## Кнопка «Передать в другой скрипт»

На экране завершённого запуска (с файлами): выбрать скрипт, сопоставить файлы с его параметрами (предложение по объявленным выходам и совпадению колонок), открывается форма запуска с подставленными значениями. Разово, связь не создаётся; рядом предложение «запускать так всегда» создаёт связь.

## CLI

Агент собирает и проверяет пайплайн без UI. Примерный вид, точные имена на усмотрение исполнителя:

- `dawg-replay link add <источник> <получатель> [--after ok|partial|any|never] [--file <файл>=<параметр>]... [--preset <имя>] [--limit-per-day N]`
- `link list`, `link show`, `link set`, `link remove`, `link enable/disable`
- `link mode <получатель> all|any [--wait 6h] [--on-timeout skip|run]`
- `link check [<скрипт>]`: проверка всей схемы (колонки, параметры, круги) без запуска
- `run <скрипт> --param <имя>=run:<id>:<файл>` и `=last:<скрипт>:<файл>[:partial]`: ссылка на результат
- `--json` у чтения, как у остальных команд.

## Скилл

- Агент выясняет у пользователя, нужен один скрипт или цепочка, и собирает цепочку из связей, а не оркестратором внутри скрипта, если пользователь не попросил иначе.
- Заполняет `outputs` у скриптов, чьи результаты идут дальше, согласует колонки с `columns` получателя.
- Собирает связи командами `link`, проверяет `link check`, предлагает пользователю посмотреть экран «Связи».
- Бамп плагина.

## Версии и приёмка

- dawg-replay 1.4.0, kit и контракт 1.4 (блок `outputs`).
- Тесты без браузера и сети: скрипты-заглушки, временный дом приложения, без системного планировщика (как сейчас, через переменные окружения для тестов).
- Приёмка руками: цепочка WB + Ozon → обновление → отчёт на заглушках, режим «после всех» со сроком и пропуском, несовпадение колонок, круг с пределом, ручная передача кнопкой, правка схемы мышкой.

## На усмотрение исполнителя

Структура таблиц (связи, передачи, режим получателя, отметки о кругах ожидания), библиотека или самописный SVG для карты (без сборщика фронтенда, как остальной UI), точные тексты, имена команд CLI в рамках описанного, механизм срабатывания срока ожидания в рамках требования выше.
