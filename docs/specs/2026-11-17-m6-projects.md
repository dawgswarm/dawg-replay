# M6: проекты (схемы из скриптов)

Заменяет в `2026-11-16-m6-pipelines.md` всё про глобальные связи, режимы получателя, круги ожидания и экран «Связи». Из того документа остаются и уже сделаны: передача файла результата в параметр `table`/`file` с проверкой колонок, ссылки `run:`/`last:` в значениях параметров, блок `outputs` (контракт 1.4), снимок источников в записи запуска и повторы с теми же файлами, кнопка «Передать в другой скрипт».

## Зачем

Пользователь собирает из своих скриптов схемы автоматизации, как в n8n: «две выгрузки карточек WB с разными пресетами отдают результат в скрипт выгрузки в Google». Один и тот же скрипт участвует в разных схемах по-разному, и схемы не должны мешать друг другу. Глобальные связи M6 (одна связь на пару скриптов, один запуск дёргает все цепочки) этого не дают.

Приложение превращается в студию автоматизации: скрипты это кирпичи, проект это программа из них. Какие кирпичи и схемы понадобятся, заранее неизвестно, поэтому приложение даёт холст, запуск и передачу файлов, а логику пишет агент вместе с пользователем.

## Цели

- Проект: своя схема из узлов и стрелок, своё расписание, кнопка «Запустить проект», своя история запусков.
- Узел: скрипт + пресет. Один скрипт может стоять в проекте несколько раз с разными пресетами.
- Запуск проекта с общим статусом; срабатывают только стрелки этого проекта. Ручной или плановый запуск скрипта вне проекта проекты не трогает.
- Проект хранится текстовым файлом: агент пишет и правит его, приложение проверяет, правки мышкой на холсте сохраняются новой версией того же файла.
- Встроенные узлы это обычные скрипты из стандартной библиотеки, поставляемой с приложением. Свой узел агент пишет по просьбе пользователя так же, как любой скрипт; он встаёт на холст наравне со встроенными.
- Ветвление без нового механизма: стрелка может идти дальше, только если источник отдал определённый файл.

## Не цели

- Код, выражения или формулы внутри стрелок и в файле проекта. Любая логика живёт в узле-скрипте.
- Параметры проекта, которые пробрасываются в узлы (дата на весь проект и т.п.). Узлы берут значения из своих пресетов; относительные даты пресетов это покрывают. Можно добавить позже.
- Циклы внутри проекта в первой версии (см. «Циклы»).
- Передача потоком или в памяти: только готовые файлы завершённых шагов.
- Совместная работа, проекты между установками.

## Анти-цели

- Непонятно, почему шаг не запустился. На схеме запуска у каждого узла статус, у пропущенного причина.
- Несовпадение колонок обнаруживается ночью посреди запуска. Видно на холсте и в `project check` до запуска.
- Проект, правленный мышкой, расходится с файлом у агента. Файл в приложении единственный источник, версии хранятся, агент перед правкой берёт текущую версию.
- Встроенные узлы как особый код приложения со своими формами настроек. Встроенный узел ничем не отличается от скрипта пользователя.

## Подход

Выбран A: запуск принадлежит проекту, срабатывают только стрелки этого проекта.

Отвергнуто:
- B: связи по-прежнему глобальные, проект только раскладывает их по холстам. Один запуск скрипта дёргает все проекты, где он есть: ровно та проблема, ради которой проекты.
- Встроенные узлы как код приложения (как в n8n). Каждый требует своего интерфейса настроек, список бесконечен. Вместо этого стандартная библиотека скриптов плюс свои узлы от агента.
- Глобальные связи M6 как есть. Не позволяют один скрипт в разных схемах и несколько раз в одной.

## Файл проекта

Текстовый файл `<имя>.project.toml`, примерно:

```toml
name = "wb-to-google"
title = "Карточки WB в Google"
description = "Два магазина, общая таблица"
timeout_minutes = 240

[[nodes]]
id = "wb1"
script = "wb-cards"
preset = "Магазин 1"
title = "WB: магазин 1"     # необязательно, по умолчанию скрипт + пресет
x = 40
y = 60

[[nodes]]
id = "wb2"
script = "wb-cards"
preset = "Магазин 2"

[[nodes]]
id = "google"
script = "google-sheets-upload"
preset = "Общая таблица"
wait = "all"                # all (по умолчанию) | any

[[edges]]
from = "wb1"
to = "google"
when = "partial"            # partial = готово или частично (по умолчанию) | ok | any
if_file = "cards.csv"       # необязательно: стрелка активна, только если источник отдал этот файл
files = [{ from = "cards.csv", to = "cards" }]   # имя, шаблон или "@main"
source_column = "Магазин"   # необязательно: при склейке добавить колонку с названием узла

[[edges]]
from = "wb2"
to = "google"
files = [{ from = "cards.csv", to = "cards" }]
```

- Узлы ссылаются на скрипты по имени и на пресеты по имени. `id` узла уникален в проекте.
- Пресет у узла необязателен: без него значения по умолчанию манифеста. У узла могут быть свои несекретные значения `values = { min_price = 1000 }` поверх пресета (удобно для стандартных узлов «Отфильтровать», «Если», чтобы не заводить пресет на каждое условие). Секретные значения только через пресет.
- Перенос на другую машину: `project export` по умолчанию кладёт в файл несекретные значения пресетов узлов (`[nodes.preset_values]`); `project add` создаёт недостающие пресеты из них, секретные параметры остаются пустыми и видны предупреждением «заполните пресет». Пресет, который уже есть с тем же именем, не перезаписывается.
- Расписание проекта и правила Telegram проекта хранятся в приложении, как у скриптов (расписание в системном планировщике), а не в файле: файл переносится между машинами без чужих расписаний.
- Приложение регистрирует проект командой `dawg-replay project add <файл>` и хранит версии (как скрипты). Правка на холсте или через CLI сохраняет новую версию. Откат к прошлой версии. Экспорт текущей версии в файл (`project export`).
- Проверка при регистрации и сохранении (как у манифеста): скрипты и пресеты существуют, параметры получателя `table`/`file` и не секретные, колонки при объявленных `outputs` (несовпадение предупреждением), нет циклов, `id` уникальны. Ошибки не дают сохранить, предупреждения видны на холсте.

## Запуск проекта

- Запуск проекта это запись в истории со своим id, статусом (идёт, готово, частично, упал, отменён), временем, кто запустил (вручную, расписание), версией проекта и шагами.
- Шаг это обычный запуск скрипта (как сейчас: журнал, файлы, экран запуска), помеченный id запуска проекта и id узла.
- Старт: запускаются узлы без входящих стрелок. Дальше узел решается, когда все входящие стрелки решены (их источники закончились или пропущены).
- Стрелка активна, если источник реально шёл и его исход подходит под `when`, и (если задан `if_file`) источник отдал этот файл. Пропущенный или не стартовавший источник даёт неактивную стрелку.
- `wait = "all"`: узел запускается, если активны все входящие стрелки; иначе пропускается с причиной («WB: магазин 2 упал»). `wait = "any"`: запускается, если активна хотя бы одна; параметры от неактивных стрелок пустые (обязательный пустой даёт «не стартовал» с причиной).
- Файлы стрелки берутся из шага-источника этого же запуска проекта. Несколько активных стрелок в один параметр `table`: строки склеиваются в порядке стрелок в файле; колонки должны совпадать (иначе шаг не стартует с причиной), `source_column` добавляет колонку с названием узла-источника. Несколько стрелок в один `file` с `multiple`: все файлы; в одиночный `file`: ошибка проверки при сохранении.
- Явное значение пресета узла для параметра, в который идёт стрелка, перекрывается стрелкой.
- Шаги идут параллельно, где схема позволяет, в пределах `max_parallel_runs` и с ожиданием слота.
- Статусы шагов: готово, частично, упал, не стартовал, отменён (человеком на экране шага), пропущен (входящая стрелка неактивна из-за исхода источника), не по этой ветке (неактивна из-за `if_file`, или все входящие стрелки идут от узлов «не по этой ветке»).
- Общий статус проекта (решение лида):
  - «упал», если хоть один шаг упал, не стартовал или отменён человеком;
  - иначе «частично», если хоть один шаг частично или пропущен. Пропущенный шаг называется в истории и в Telegram отдельной строкой («пропущен: Google, WB: магазин 2 закончился частично, а стрелка ждёт готово»), чтобы схема не «молча не дошла»;
  - иначе «готово». Шаги «не по этой ветке» это нормальный путь и статус не портят.
  - Тихая поломка шага (`suspicious`) переносится на проект как у скрипта: строкой в итоге, статус не меняет.
- По умолчанию `when` у стрелки в проекте «ok или partial» (`partial`): выгрузки часто заканчиваются частично, а получатель обычно должен идти с тем, что собрано. Строже (`ok`) ставится явно.
- Таймаут запуска проекта (`timeout_minutes`): по истечении идущие шаги отменяются, нерешённые пропускаются, статус «упал (таймаут)».
- «Остановить» отменяет идущие шаги и пропускает остальные.
- «Перезапустить с упавшего»: новый запуск проекта по той же версии проекта, что прошлый (запуск проекта хранит версию и соответствие узлов шагам). Шаги со статусом «готово» не повторяются, их файлы берутся из прошлого запуска; «частично», упавшие, не стартовавшие, отменённые и пропущенные идут заново; «не по этой ветке» решаются заново по новым исходам. Запустить по текущей версии это обычный «Запустить проект».
- Новый запуск проекта, пока предыдущий ещё идёт: плановый пропускается с причиной («предыдущий запуск ещё идёт») и даёт уведомление `failed`, как пропуск у расписания скрипта; ручной получает отказ «Проект уже запущен» с предложением открыть идущий или остановить его. Два запуска одного проекта одновременно не идут.
- Своего демона у приложения нет. Кто продвигает запуск проекта (отдельный процесс-ведущий на время запуска, или решения при завершении каждого шага, как сделано в dr-106), на выбор исполнителя. Требования: запуск проекта доходит до конца без открытого UI; падение процесса не оставляет запуск проекта «идущим» навсегда (как `recover_lost` у запусков); выключенный компьютер обрабатывается как у обычных запусков (потерянные шаги, статус упал с причиной).

## Циклы

В первой версии циклов нет: файл с циклом не сохраняется. Повторы и обход страниц делаются внутри узла-скрипта. Если понадобится, позже: обратная стрелка с пределом проходов за запуск.

## Стандартная библиотека узлов

Обычные скрипты по контракту, без браузера и без ключа DAWG, поставляются с приложением и регистрируются при установке или обновлении (обновляются вместе с приложением, пользовательские скрипты не трогают). На холсте в палитре узлов отдельной группой, в библиотеке скриптов под своим фильтром.

Первый набор (на усмотрение исполнителя в рамках смысла):
- «Склеить таблицы»: несколько таблиц в одну, с колонкой источника или без.
- «Отфильтровать строки»: условие на колонку (равно, содержит, больше, меньше, пусто), отдаёт `rows.csv` и, если ничего не осталось, ничего (для ветвления).
- «Если»: по условию на таблицу (строк больше N, есть строка с условием) отдаёт `yes.csv` или `no.csv`; стрелки дальше с `if_file`.
- «Выбрать и переименовать колонки».

Свой узел: агент пишет по просьбе пользователя обычный скрипт (часто без браузера), объявляет `outputs`, регистрирует, ставит в проект.

## Telegram

- Шаги проекта своих сообщений об итоге не шлют. Вопросы скрипта (`kit.ask`) идут сразу, как сейчас, с названием проекта и узла.
- Итог проекта одним сообщением: «Готово: <проект>», статусы шагов строкой («5 из 6, пропущен: Google»), упавший шаг и причина, длительность. Ключи правил как у скрипта (`failed`, `done_scheduled`, `done_manual`, `suspicious`, `attach_main` не применяется), уровни: общие настройки, проект, расписание проекта, запуск.

## Интерфейс

- Экран «Проекты» вместо «Связи»: список (название, расписание, последний запуск и статус, «Запустить»), «Новый проект», «Импорт файла».
- Холст проекта: узлы (скрипт, пресет, последний статус узла в последнем запуске), стрелки с подписями (`cards.csv → cards`, условие, `if_file`), палитра узлов (скрипты пользователя и стандартная библиотека), добавить узел, выбрать пресет, протянуть стрелку, панель стрелки и узла, перетаскивание с сохранением положения в файле проекта, ошибки и предупреждения проверки на холсте. Сохранение даёт новую версию; версии и откат.
- Экран запуска проекта: тот же холст со статусом каждого шага, переход к шагу, причины пропуска, «Остановить», «Перезапустить с упавшего».
- Расписание и правила Telegram проекта на странице проекта.
- Страница скрипта: «Входит в проекты: …» со ссылками.
- Экран запуска шага: «Шаг проекта <проект>, узел <узел>», откуда пришли файлы (уже есть: «Запущен после», «из результата …»).
- Кнопка «Передать в другой скрипт» остаётся; «запускать так всегда» заменяется на «Добавить в проект…» (новый или существующий: два узла и стрелка; пресет узлов как у запусков, без пресета, если запуск шёл без него).
- Блок связей на странице скрипта, экран «Связи», «из результата …» как связь в форме: убираются. Ссылки `run:`/`last:` в форме, пресете и расписании остаются.

## CLI

Точные имена на усмотрение исполнителя:
- `dawg-replay project add|update <файл>`, `project list`, `project show <имя> [--version N]`, `project export <имя> [-o файл]`, `project check <файл|имя>`, `project remove <имя>`, `project versions`, `project rollback`.
- `project run <имя> [--follow] [--json]`, `project runs <имя>`, `project stop <id>`, `project retry <id>` (с упавшего).
- `project schedule ...` как у скриптов, правила Telegram проекта как у скриптов.
- Команды `link ...` убираются.

## Что из сделанного в M6 меняется

- Убираются: таблицы `links`, `link_files`, `link_targets`, `link_log`, `link_rounds`, `link_pending` (миграция, удаляющая их; M6 не выпущен, данных у пользователей нет), модуль `chain` в нынешнем виде, `cli_link`, экран «Связи», блок на странице скрипта, процесс ожидания сроков.
- Переиспользуются: подстановка файлов в `launch.prepare` (по шагам вместо связей), проверка таблиц, `outputs` и `outputs.script_outputs`, снимок `inputs` и повторы, экран запуска с источниками, `record_not_started`, правила Telegram, демо-скрипты.
- Скилл: вместо раздела про связи раздел про проекты: схема словами с клиентом, узлы как скрипт + пресет, файл проекта, `project check`, пробный `project run --follow`, свой узел-скрипт для нестандартной обработки, стандартные узлы, «откройте проект в приложении». Бамп плагина.

## Версии и приёмка

- dawg-replay 1.4.0, kit и контракт 1.4 (без изменений к уже сделанному, если исполнитель не найдёт нужды).
- Тесты без браузера и сети, без системного планировщика.
- Демо: проект «два источника → склейка → получатель» на заглушках, ветвление через «Если», отмена и перезапуск с упавшего.
- Приёмка руками по плану `docs/acceptance/m6-projects.md`.
