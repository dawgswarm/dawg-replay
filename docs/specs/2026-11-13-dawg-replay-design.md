## 1. Зачем это

У клиентов DAWG задачи по сбору данных очень разные: карточки товаров на маркетплейсе, статистика матчей, объявления, цены. Делать отдельный продукт под каждую задачу нельзя. Писать парсер руками клиент обычно не хочет или не умеет.

Идея: кодинг-агент (Claude Code или Codex) со скиллом один раз сам проходит весь пайплайн через браузер DAWG и затем превращает найденный путь в обычный переиспользуемый скрипт. Скрипт попадает в локальное приложение. Там клиент его запускает, меняет параметры, следит за прогрессом и смотрит историю запусков.

Агент нужен только для создания и починки скрипта. Обычный запуск детерминированный, идёт без агента и токенов, клиент платит только минутами DAWG.

### Урок предыдущей попытки

Предыдущий проект `dawg_kennel` с похожими идеями (профили, расписания, раннер скриптов, GUI) делали всё сразу, и в итоге он не работает. Из него берём только идеи. Правила для этого проекта:

- сначала один вертикальный срез, который работает от начала до конца (раздел 9), ширина потом;
- в первой версии нет ничего лишнего для основного сценария (раздел 3.2);
- каждый этап закрывается живой проверкой на настоящем сайте с настоящим ключом DAWG; юнит-тестов для закрытия этапа мало.

## 2. Пользователь и сценарии

Пользователь: клиент DAWG на своём компьютере (macOS, Windows, Linux). У него есть Claude Code или Codex, ключ DAWG и подключённый `dawg-mcp`. Читать код он может не уметь.

### Сценарий A. Создание

1. Клиент пишет агенту, например: «Собирай карточки с Ozon по запросу X: название, цена, рейтинг, продавец. Сохраняй в Google-таблицу».
2. Агент по скиллу уточняет задачу: что собирать, что клиент захочет менять между запусками, что считать единицей прогресса, куда отдавать данные.
3. Агент сам проходит пайплайн инструментами `dawg-mcp` (`browser_*`, `scrape_*`): открывает сайт, разбирается в структуре, пагинации и антиботе, ищет внутренние JSON-API.
4. Агент пишет скрипт по контракту (раздел 5), прогоняет его через `dawg-replay` на маленьких параметрах и правит, пока прогон не пройдёт.
5. Агент регистрирует скрипт в `dawg-replay` и говорит клиенту, где его найти.

### Сценарий B. Запуск

1. Клиент открывает веб-интерфейс `dawg-replay` и выбирает скрипт.
2. В форме, построенной по параметрам скрипта, меняет число страниц, список ссылок и так далее. Может выбрать сохранённый пресет.
3. Нажимает «Запустить» и видит прогресс, метрики, лог и результаты. Может отменить запуск.
4. Позже смотрит историю запусков и скачивает выходные файлы.

### Сценарий C. Починка

1. Сайт поменялся, запуск падает.
2. Клиент просит агента починить скрипт. Агент читает лог упавшего запуска через CLI `dawg-replay`, заново проходит проблемное место в браузере, правит тот же скрипт и регистрирует новую версию. Старая версия сохраняется.

## 3. Цели и границы

### 3.1 Цели

- Агент со скиллом стабильно доводит сценарий A до рабочего скрипта на типичном сайте (маркетплейс, спортивная статистика).
- Скрипт запускается без агента: из приложения, из CLI или напрямую через `uv run script.py`.
- Всё, что клиент может захотеть поменять, вынесено в параметры и редактируется в UI без правки кода.
- Прогресс и результаты показываются по единому контракту рендера. Агент подгоняет под него вывод конкретной задачи.
- Упавший или отменённый запуск не оставляет живых браузеров DAWG и не жжёт минуты.

### 3.2 Не входит в v1

- Расписания (подтверждено заказчиком). Для регулярных запусков хватит `dawg-replay run <script> --preset <p>` из cron или Планировщика задач Windows. В документации нужен пример.
- Сайты под логином, хранение куки и профилей между запусками (подтверждено заказчиком). В v1 только публичные данные.
- Редактирование кода скрипта в UI. В v1 код можно только посмотреть, правит его агент.
- Встроенные выгрузки (Sheets, БД, Telegram). Куда отдавать данные, решает сам скрипт.
- Облачный запуск, несколько пользователей, доступ с другой машины.
- Обмен скриптами между клиентами.

### 3.3 Что считаем провалом, даже если всё технически работает

- Скрипт работает только при агенте рядом: захардкожены значения из разведки, есть зависимость от сессии MCP или ручные шаги.
- После падения или отмены в DAWG остаются браузеры, и клиент платит за минуты, которые не использовал.
- Для установки приложения нужен бинарник, подпись кода или установщик.
- Любой сайт, открытый в браузере клиента, может обратиться к локальному веб-интерфейсу (CSRF, DNS rebinding).
- Приложение умеет много всего, но основной сценарий в нём не доведён до конца.

## 4. Состав и доставка

Три части в двух репозиториях:

| Часть | Что это | Репозиторий | Доставка |
|---|---|---|---|
| `dawg-replay` | Python-пакет: ядро, CLI, локальный веб-интерфейс | `dawgswarm/dawg-replay` | PyPI, `uv tool install dawg-replay` |
| `dawg-replay-kit` | Маленькая библиотека для скриптов: параметры, события, браузеры DAWG | тот же репозиторий, второй пакет | PyPI, указывается в PEP 723-заголовке скрипта |
| `dawg-replay-builder` | Скилл: `SKILL.md`, справочные файлы, шаблон скрипта | `dawgswarm/dawg-replay-builder` | Claude Code: плагин через marketplace (скилл и конфиг `dawg-mcp`). Codex: папка скилла копируется в каталог скиллов Codex, MCP настраивается по README `dawg-mcp` |

Контракт скрипта (раздел 5) связывает обе стороны. Он лежит в репозитории `dawg-replay` в `docs/contract.md`, имеет версию (`contract = 1`) и копируется в скилл как справочный файл. Скрипт с неизвестной мажорной версией контракта приложение не запускает и прямо пишет почему.

Протокол состоит из обычных файлов и JSON Lines, поэтому скрипт может выполнять его и без `dawg-replay-kit`. Скилл всё равно всегда использует kit, чтобы скрипты были однообразными.

Что нужно у клиента: `uv` (им запускаются скрипты), Python 3.10 или новее, ключ DAWG. Локальный браузер не нужен: скрипты подключаются к облачному Chromium DAWG по CDP, так же как `dawg-mcp`.

## 5. Контракт скрипта (v1)

### 5.1 Форма

Скрипт состоит из одного файла `script.py`. В начале два блока комментариев:

1. Стандартный блок PEP 723 с зависимостями (`dawg-sdk-python`, `playwright`, `dawg-replay-kit` и всё, что нужно задаче). `uv run` даёт каждому скрипту изолированное окружение, приложению не приходится управлять venv.
2. Манифест в той же форме, тип блока `dawg-script`, внутри TOML:

```python
# /// script
# requires-python = ">=3.10"
# dependencies = ["dawg-replay-kit>=1,<2", "dawg-sdk-python>=0.4,<0.5", "playwright>=1.58,<2"]
# ///

# /// dawg-script
# contract = 1
# name = "ozon-search-cards"          # slug, уникальный в приложении
# title = "Ozon: карточки по поисковому запросу"
# description = "Обходит выдачу Ozon по запросу и собирает название, цену, рейтинг и продавца."
# version = 3                         # растёт при каждой правке
# timeout_minutes = 60                # предел длительности одного запуска
#
# [[params]]
# name = "query"
# type = "string"
# title = "Поисковый запрос"
# required = true
#
# [[params]]
# name = "max_pages"
# type = "int"
# title = "Сколько страниц выдачи обойти"
# default = 5
# min = 1
# max = 100
#
# [[params]]
# name = "sheet_token"
# type = "secret"
# title = "Токен Google Sheets"
# ///
```

Манифест читается статически: без запуска скрипта и без установки его зависимостей.

### 5.2 Типы параметров

`string`, `text` (многострочный), `int`, `float`, `bool`, `enum` (`choices = [...]`), `url`, `url_list`, `string_list`, `secret`.

Общие поля: `name`, `type`, `title`, `description?`, `required?`, `default?`. Для чисел есть `min?` и `max?`, для списков `max_items?`.

`secret` хранится в системном keyring (библиотека `keyring`). В пресеты и файлы запусков он не попадает, в UI маскируется. Kit заменяет значения секретов на `***` во всех событиях, которые через него проходят.

### 5.3 Окружение запуска

Приложение запускает `uv run script.py` отдельным процессом и передаёт переменные:

| Переменная | Значение |
|---|---|
| `DAWG_API_KEY` | ключ из настроек приложения |
| `DAWG_BASE_URL` | если задан в настройках |
| `DAWG_SCRIPT_PARAMS` | путь к JSON с проверенными значениями параметров, секреты подставлены |
| `DAWG_SCRIPT_EVENTS` | путь к файлу событий (JSON Lines), скрипт пишет туда |
| `DAWG_SCRIPT_OUTPUT_DIR` | каталог этого запуска для выходных файлов |
| `DAWG_SCRIPT_RUN_ID` | id запуска |

Автономный режим. Если переменных нет (скрипт запущен руками), kit берёт параметры из `--params file.json` или из аргументов вида `--max-pages 3`, для остальных берёт `default`. Секреты читаются из переменных окружения `DAWG_SECRET_<ИМЯ_ПАРАМЕТРА>`, keyring в этом режиме не используется. Если обязательный параметр не задан, kit завершает работу и пишет, какого аргумента не хватает. События печатаются в stderr в читаемом виде, файлы пишутся в `./output/`. Ключ берётся из `DAWG_API_KEY`.

stdout и stderr процесса приложение сохраняет как сырой лог.

### 5.4 Контракт рендера (события)

Это список того, что приложение умеет показывать. Агент подгоняет данные любой задачи под эти типы и новых не придумывает. Каждая строка файла событий содержит JSON-объект с полями `t` (тип), `ts` (время в ISO, его ставит kit) и полями конкретного типа.

| `t` | Поля | Как показывается |
|---|---|---|
| `log` | `level` (`debug`/`info`/`warn`/`error`), `msg` | строка в ленте лога, цвет и фильтр по уровню |
| `stage` | `name` | текущий шаг в шапке запуска и отметка на таймлайне |
| `progress` | `id`, `label`, `done`, `total?` | полоска прогресса; без `total` просто счётчик. Каждый `id` даёт свою полоску, новое значение заменяет старое |
| `metric` | `key`, `label`, `value` (число или строка), `unit?` | плитка с подписью и значением, новое значение заменяет старое |
| `rows` | `table`, `columns?`, `rows` (список объектов) | превью таблицы. Приложение держит до 500 строк на таблицу; полные данные скрипт сохраняет сам |
| `artifact` | `path` (внутри output dir), `label`, `mime?` | файл в блоке «Результаты»: скачать или открыть папку |
| `session` | `action` (`provisioning`/`open`/`close`), `session_id` (кроме `provisioning`), `browser_id?` | служебное: учёт браузеров запуска (5.6), в UI счётчик открытых браузеров |
| `result` | `status` (`ok`/`partial`/`failed`), `summary` (короткий текст, markdown) | итоговая карточка запуска |

Правила:

- Неизвестный `t` или битая строка показываются в логе как сырая строка с пометкой. Экран от них не ломается.
- Итог запуска определяют код выхода и последнее событие `result`. Выход 0 без `result` считается `ok`. Ненулевой выход всегда даёт `failed`, даже если был `result: ok`.
- API kit примерно такой: `kit.progress("cards", "Карточки", done, total)`, `kit.metric(...)`, `kit.rows("cards", [...])`, `kit.artifact(path, "CSV")`, `kit.stage(...)`, `kit.log.info(...)`, `kit.result(...)`, `kit.params` с типизированным доступом.
- Kit сам прореживает `progress` и `metric` (например, не чаще 4 раз в секунду на `id`), так что скрипт может вызывать их в цикле.

Новый тип события меняет контракт. Если старое приложение может безопасно показать его как сырую строку, поднимается минорная версия, иначе мажорная.

### 5.5 Данные

Куда уходят данные, решает скрипт: CSV или JSON в output dir, Google-таблица, база, бот. Приложение данные не разбирает. Оно показывает превью из `rows` и файлы из `artifact`. Скилл требует, чтобы при падении на середине скрипт сохранял уже собранное и отдавал `result: partial`.

### 5.6 Браузеры DAWG и деньги

- Скрипт получает браузер через kit (обёртка над `dawg-sdk-python` и подключение Playwright по CDP). Kit пишет события `session` и закрывает браузер в `finally` и по сигналу отмены.
- Идентификаторы. Браузер освобождается по `session_id` (`DELETE /api/v1/browsers/{session_id}`, в SDK `release(session_id)`). `browser_id` (`browserInstanceId`) нужен только для отображения.
- Порядок событий. `session provisioning` kit пишет до запроса на создание. `session open` с `session_id` пишет сразу после ответа на POST, до ожидания готовности браузера. Ожидание может занять до 2 минут, и убийство процесса в этот момент даёт самый вероятный сценарий утечки. Сейчас `create()` в `dawg-sdk-python` делает POST и ожидание одним вызовом и отдаёт id только в конце. Нужна небольшая доработка SDK: колбэк после POST или раздельные `start()` и `wait_ready()`. Эта доработка входит в M1.
- Страховка в приложении. После завершения процесса с любым исходом приложение находит все `session_id` с событием `open` без `close` и освобождает их через `dawg-sdk-python`. Результат пишется в лог запуска. Это главная защита от утечки минут, она обязательно покрыта тестом.
- Остаточное окно. Если процесс убит между отправкой POST и ответом (есть `provisioning`, нет `open`), id браузера неизвестен. Освобождать все сессии ключа нельзя: на том же ключе живут браузеры `dawg-mcp` и других запусков. В этом случае приложение показывает в логе и в UI предупреждение «возможно, остался браузер» со списком сессий ключа, созданных в этом окне (`list_sessions`, поле `startedAt`), и кнопкой освободить их вручную. Полностью окно закрыла бы метка сессии на стороне платформы (поле `label` при создании и фильтр в списке). В v1 её не делаем, заказчик согласен на предупреждение.
- Лимит браузеров тарифа. Если платформа отказала в браузере (429 или лимит), kit несколько раз повторяет запрос с паузой `retry_after`, потом запуск падает с сообщением «достигнут лимит одновременных браузеров тарифа». Свободное место заранее не проверяем.
- Сколько браузеров параллельно открывает один скрипт, решает скрипт, но лимит kit требует указать явно. По умолчанию 1.

### 5.7 Отмена и таймаут

- Отмена: мягкий сигнал (SIGTERM, на Windows CTRL_BREAK_EVENT группе процессов), через 15 секунд kill всего дерева процессов. Затем страховка из 5.6.
- Превышение `timeout_minutes` (верхний предел задаётся в настройках приложения) запускает ту же процедуру, статус запуска `failed (timeout)`.

## 6. Приложение dawg-replay

### 6.1 Архитектура

Ядро написано как Python-библиотека, CLI и локальный веб-сервер работают поверх него и своей логики не содержат. Состояние хранится в SQLite и файлах в каталоге данных. Веб-стек выбирает команда с одним ограничением: приложение ставится одной командой `uv tool install` и не требует Node на машине клиента. Фронтенд собирается при релизе и кладётся в пакет, либо используется серверный рендер (htmx и подобное).

### 6.2 Хранение

```
~/.dawg-replay/                    (через platformdirs, на Windows и macOS свои пути)
  config.toml                      base url, лимиты; ключ DAWG лежит в keyring
  db.sqlite                        скрипты, версии, пресеты, запуски
  scripts/<name>/v<version>/script.py
  runs/<run_id>/params.json        (без секретов)
              events.jsonl
              stdout.log  stderr.log
              output/
```

Регистрация скрипта с уже существующим `name` создаёт новую версию, старые остаются. Любую версию можно запустить или сделать текущей.

### 6.3 CLI

CLI в основном использует агент. У всех команд есть флаг `--json` с машиночитаемым выводом, ошибки валидации понятны без UI.

```
dawg-replay config set-key                 # спрашивает ключ, кладёт в keyring
dawg-replay validate <file>                # проверить манифест и контракт без регистрации
dawg-replay add <file>                     # зарегистрировать или обновить (новая версия)
dawg-replay list | show <name>
dawg-replay versions <name> | rollback <name> <version>
dawg-replay run <name|file> [--params p.json | --set k=v ...] [--preset p] [--follow]
dawg-replay runs [<name>] | logs <run_id> [--events] | cancel <run_id>
dawg-replay preset save|list|delete <name> ...
dawg-replay secret set <name> <param>
dawg-replay remove <name>
dawg-replay ui [--port N] [--no-open]
dawg-replay --version [--json]             # версия приложения и поддерживаемые версии контракта
```

`run <file>` запускает незарегистрированный файл. Агенту это нужно для тестовых прогонов во время создания. Такие запуски помечаются как черновые.

### 6.4 Веб-интерфейс

- Сервер слушает только 127.0.0.1 на случайном порту. При старте он генерирует токен и открывает браузер на URL с токеном, токен сохраняется в cookie. Запросы без токена отклоняются, заголовок `Host` проверяется (защита от DNS rebinding).
- Экраны:
  1. Скрипты. Список: название, описание, последний запуск (статус и время), кнопка «Запустить».
  2. Скрипт. Описание, форма параметров по манифесту с валидацией, пресеты (выбрать, сохранить текущие значения), «Запустить», история запусков, просмотр кода только для чтения, версии.
  3. Запуск. Обновляется в реальном времени по событиям из 5.4 (SSE или WebSocket): статус, текущий шаг, полоски прогресса, метрики, превью таблиц, лента лога с фильтром, файлы-результаты, счётчик открытых браузеров, кнопка «Отменить». После завершения показывается итоговая карточка `result`.
  4. Настройки. Ключ DAWG с проверкой, лимит параллельных запусков, предел таймаута. По желанию остаток минут через API usage.
- UI показывает и запуски, начатые из CLI. История общая, текущее состояние читается из `events.jsonl`.
- Внешний вид выбирает команда. Обязательное требование одно: экран запуска понятен человеку, который не читает код.

### 6.5 Параллельные запуски

Можно запускать несколько скриптов одновременно, в том числе один скрипт несколько раз. Лимит задаётся в настройках, по умолчанию 3. При превышении приложение отказывает и объясняет причину. Очереди в v1 нет, она появится вместе с расписаниями.

### 6.6 Жизненный цикл процессов

Запуск живёт дочерним процессом того, кто его начал: CLI (с `--follow` или без) или сервера UI. При закрытии сервера UI его запуски отменяются по 5.7 и проходят страховку 5.6, осиротевших процессов остаться не должно. Запуск из CLI без `--follow` работает в фоне. Как именно отвязать процесс, решает команда; `dawg-replay cancel` обязан работать на всех трёх ОС. При старте приложение ищет запуски в статусе «идёт», чьих процессов уже нет, ставит им `failed (lost)` и прогоняет для них страховку 5.6.

## 7. Скилл dawg-replay-builder

### 7.1 Формат

Стандартный `SKILL.md` (общий формат Agent Skills, его понимают Claude Code и Codex) и справочные файлы:

- `contract.md`: копия контракта нужной версии;
- `template.py`: эталонный скрипт со всеми приёмами (браузер через kit, повторы, пагинация, прогресс, частичное сохранение);
- `exploration.md`: как разведывать сайт через `dawg-mcp`;
- `checklist.md`: проверки перед регистрацией.

В начале скилл проверяет, что `dawg-mcp` подключён (есть инструменты `browser_*`) и что `dawg-replay` установлен и поддерживает нужную версию контракта (`dawg-replay --version --json`). Если чего-то нет, скилл объясняет клиенту, как это поставить, и дальше не идёт.

### 7.2 Создание скрипта (сценарий A)

1. Разговор с клиентом. Что собрать, откуда, какие поля. Что клиент будет менять между запусками (это станут параметры). Что считать единицей прогресса. Примерный объём. Куда отдавать данные (отсюда код выгрузки и, возможно, параметры типа `secret`). Коротко, без допроса.
2. Разведка. Агент проходит пайплайн целиком на 1-2 реальных примерах через `dawg-mcp`. Сначала ищет внутренние JSON-API и данные в странице (`__NEXT_DATA__` и подобное): они устойчивее DOM. Выясняет пагинацию, ленивую подгрузку, антибот, нужны ли прокси или гео. Записывает находки (эндпоинты, селекторы, особенности), они пойдут в комментарии скрипта.
3. Сборка скрипта по `template.py`. Правила:
   - всё, что клиент может менять, вынесено в параметры; значения из разведки в коде не захардкожены;
   - селекторы устойчивые: роли, data-атрибуты, тексты; позиционных селекторов нет; если есть API, используется API;
   - повторы с паузами, умеренная скорость, явные таймауты;
   - браузер только через kit, лимит параллельных браузеров указан явно;
   - прогресс по согласованной единице, метрики, превью `rows`, `artifact` для файлов, `result` в конце;
   - собранное сохраняется по ходу работы, падение на середине даёт `partial`;
   - в шапке скрипта комментарий: откуда данные, что найдено при разведке, дата.
4. Проверка. `dawg-replay validate`, затем `dawg-replay run <file> --set max_pages=1 ... --json --follow`. Агент читает события и выходные файлы и сверяет, что данные те, что просили; кода выхода 0 для этого недостаточно. Повторяет, пока не пройдёт.
5. Регистрация. `dawg-replay add`, затем агент объясняет клиенту, как открыть UI и что значат параметры.

### 7.3 Починка (сценарий C)

`dawg-replay runs <name> --json`, затем `dawg-replay logs <run_id> --events`. Агент находит место поломки, заново проходит его через `dawg-mcp`, правит тот же файл, поднимает `version`, проверяет по шагу 4 и делает `add`. Новый скрипт с нуля пишется только по просьбе клиента.

### 7.4 Минуты при разведке

Скилл требует освобождать браузеры `dawg-mcp` (`browser_release`) сразу после разведки и не держать их открытыми, пока агент пишет код.

## 8. Безопасность

- Скрипты выполняются без песочницы, с правами пользователя. Их пишет агент клиента на машине клиента, это осознанный выбор. Обмена скриптами нет, поэтому чужой код в приложение не попадает. В README это сказано прямо.
- Ключ DAWG и секреты лежат в keyring. В БД, пресетах, `params.json` запуска и логах их нет.
- Веб-интерфейс защищён по 6.4.

## 9. Этапы

Каждый этап закрывается живой проверкой с настоящим ключом на настоящем сайте. Следующий этап начинается, когда предыдущий работает целиком.

- M1, контракт и запуск. `contract.md` v1, `dawg-replay-kit`, ядро и CLI (`validate`, `add`, `run`, `runs`, `logs`, `cancel`, пресеты, секреты), страховка 5.6, доработка `dawg-sdk-python` из 5.6. Один скрипт написан руками по контракту (например, Ozon по запросу) и работает из CLI и автономно. Проверка: отмена посреди запуска и `kill -9` процесса скрипта не оставляют живых браузеров.
- M2, скилл. `dawg-replay-builder` с шаблоном и справкой. Проверка: агент в чистой сессии Claude Code и Codex по одной фразе клиента создаёт рабочие скрипты для трёх сайтов: маркетплейс (Ozon или Wildberries), сайт спортивной статистики, Avito. Скрипт считается рабочим, если три запуска подряд с разными параметрами дают правильные данные (выборка сверяется руками) и проходят проверки M1. Отдельно проверяется починка намеренно сломанного скрипта.
- M3, веб-интерфейс. Экраны из 6.4 поверх того же ядра. Проверка: человек без CLI запускает скрипт из M2 с другими параметрами, видит прогресс, отменяет запуск, скачивает результат.
- M4, доставка. Релизы на PyPI, плагин Claude Code в marketplace, инструкция для Codex, README «от установки до первого скрипта», пример с cron.

## 10. Критерии приёмки v1

1. Новый пользователь с ключом DAWG и Claude Code или Codex по README проходит путь: установил, попросил агента, получил скрипт, запустил его из UI с другими параметрами. Помощь команды не нужна.
2. Любой зарегистрированный скрипт запускается автономно через `uv run script.py`, если обязательные параметры переданы аргументами, а секреты переменными `DAWG_SECRET_*`.
3. Отмена, таймаут, убийство процесса скрипта и закрытие UI не оставляют открытых браузеров DAWG (проверка через `list_sessions`), если процесс успел получить ответ на создание браузера. Для остаточного окна из 5.6 пользователь видит предупреждение и освобождает браузер одним нажатием.
4. Форма в UI строится по манифесту для всех типов из 5.2, невалидные значения в запуск не уходят.
5. Все типы событий из 5.4 показываются правильно, неизвестные типы экран не ломают.
6. Веб-интерфейс не отвечает на запросы без токена и с чужим `Host`.
7. Всё работает на macOS, Windows и Linux.

## 11. Принятые решения

Подтверждено заказчиком:

- расписаний в v1 нет;
- сайтов под логином в v1 нет;
- метку сессии в платформе в v1 не делаем, остаточное окно закрывается предупреждением (5.6).

Решения автора спеки, команда может их пересмотреть:

- тип параметра `secret` есть в v1, потому что данные часто уходят во внешние сервисы с токенами;
- `dawg-replay-kit` выпускается отдельным пакетом из репозитория `dawg-replay`;
- события пишутся в файл из `DAWG_SCRIPT_EVENTS`; stdout для них не используется, чтобы `print` в скрипте не ломал протокол;
- лимит параллельных запусков 3, превью таблиц 500 строк, мягкая отмена 15 секунд;
- доработка `dawg-sdk-python` (id сессии сразу после POST) входит в M1;
- при лимите браузеров тарифа делаем повторы и показываем понятную ошибку, свободное место заранее не проверяем;
- секреты в автономном режиме берутся из `DAWG_SECRET_*`;
- сайты для приёмки M2 и порог «три успешных запуска подряд».

## 12. Решает команда

Веб-стек и дизайн UI. Устройство ядра и схема БД. Способ фонового запуска из CLI на каждой ОС. Структура плагина Claude Code и путь установки для Codex (сверить с актуальной документацией обоих). Детали API `dawg-replay-kit` в рамках 5.4.
