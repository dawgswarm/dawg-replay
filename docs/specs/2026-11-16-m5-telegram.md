# M5, часть 1: уведомления в Telegram

## Зачем

Запуск по расписанию или долгий ручной запуск идёт, когда пользователя нет у экрана. Сейчас он узнаёт об итоге, падении или вопросе скрипта (`kit.ask`, код из SMS) только открыв приложение; вопрос по расписанию почти всегда уходит в таймаут. Нужно, чтобы приложение само писало пользователю в Telegram и принимало ответ на вопрос оттуда же.

## Цели

- Личный бот пользователя: каждый создаёт своего бота у @BotFather, сообщения приходят ему в личку. Один бот и один чат на установку приложения.
- Пользователь сам выбирает, о чём и когда ему пишут: общие настройки, переопределение у скрипта и у расписания, переключатель на форме запуска.
- Ответ на вопрос скрипта прямо из Telegram, включая секретный (код), с удалением сообщения с кодом.
- Работает для запусков из UI, `dawg-replay run` (фон и `--follow`) и по расписанию, без открытого UI.

## Не цели

- Чаты групп, несколько адресатов, разные чаты у разных скриптов.
- Общий бот DAWG; Telegram Serverless (нельзя вызвать извне, своя среда на JS, ничего не добавляет: приложение само ходит в Bot API).
- Вебхук на итог, запуск по ссылке и по папке, фоновая служба: следующие части M5.
- Изменения контракта и kit. Скрипт, как и раньше, может сам отправить что угодно своим `secret`-параметром.

## Анти-цели

- Падение или недоступность Telegram влияет на итог запуска. Отправка best effort, ошибка видна в журнале запуска и в настройках («последняя ошибка отправки»), запуск её не замечает.
- Токен бота или секретный ответ попадает в БД, историю, логи, события, экспорт.
- Чужой человек, написавший боту, может ответить на вопрос или привязать чат.
- Акцент на минутах DAWG в текстах уведомлений.

## Подход

Сообщения отправляет и ответы принимает сам процесс, который ведёт запуск (`launch.supervise`: процесс-супервизор фонового запуска, `run --follow`, поток сервера UI), напрямую через Bot API (`sendMessage`, `sendDocument`, `getUpdates`, `answerCallbackQuery`, `deleteMessage`) по HTTPS.

Отвергнуто:
- отправка из скрипта через kit: каждый скрипт должен это уметь, токен попал бы в скрипт;
- отдельная постоянная служба: нужна только для запуска по ссылке, это следующая часть M5;
- Telegram Serverless: см. «Не цели».

## Подключение

- Настройки, блок Telegram:
  1. Поле токена. Токен хранится в системном хранилище паролей рядом с ключом DAWG (`SecretStore`), проверяется `getMe`, показывается имя бота.
  2. Привязка чата по одноразовому коду: приложение показывает ссылку `https://t.me/<бот>?start=<код>` (кнопка «Открыть в Telegram») и команду `/start <код>` для ручного ввода, ждёт (`getUpdates`, до ~5 минут) именно этот `/start <код>` и запоминает `chat_id` и имя собеседника, бот отвечает «Подключено к dawg-replay». `/start` без кода или с чужим кодом не привязывает. Пока чат привязан, сообщения из других чатов игнорируются.
  3. «Отправить проверочное», «Отключить» (стирает токен и чат).
- CLI: `dawg-replay telegram connect` (запрос токена через getpass, ожидание /start), `telegram test`, `telegram status`, `telegram disconnect`, `telegram set <событие> on|off` и порог долгого запуска.
- `chat_id` и галочки хранятся в `config.toml`, токен только в хранилище паролей.
- Настройка адреса Bot API (`telegram_api_url`, по умолчанию `https://api.telegram.org`): для своего сервера Bot API или зеркала, если у пользователя Telegram доступен не напрямую. Системный прокси учитывается как у остальных запросов приложения.

## События и выбор пользователя

События:

| Ключ | Когда | По умолчанию |
|---|---|---|
| `failed` | запуск упал, таймаут, ошибка старта, потерян (`lost`), не стартовал по расписанию (`not_started`), плановый пропущен без слота (`skipped`) | вкл |
| `ask` | скрипт задал вопрос | вкл |
| `done_scheduled` | запуск по расписанию закончился успешно | вкл |
| `done_manual` | ручной запуск закончился успешно | «если шёл дольше N минут», N = 10 |
| `suspicious` | тихая поломка (`repair.suspicion`), в дополнение к итогу | вкл |
| `attach_main` | приложить главный файл итога (`main`) к сообщению об итоге | выкл |

Для `done_manual` значения: всегда / если дольше N минут / никогда.

Статусы: `ok` и `partial` дают `done_*` (для `partial` в тексте «частично» и число упавших строк); отмена пользователем и отмена из-за остановки сервера UI (`cancelled`) сообщения не дают; черновые запуски (разработка скрипта агентом) не дают ничего.

Уровни, побеждает самый конкретный:

1. Запуск: на форме запуска выбор «Сообщить, когда закончится»: «по настройкам» (по умолчанию, рядом подсказка, что это значит сейчас, например «если дольше 10 минут»), «всегда», «нет». В CLI без флага по настройкам, `--notify` всегда, `--no-notify` нет. Выбор касается только сообщения об успешном итоге (`done_*`, с ним `suspicious`); падения и вопросы идут по настройкам. Выбор сохраняется в записи запуска, потому что итог может отправить другой процесс.
2. Расписание: «как у скрипта» или свои значения.
3. Скрипт: на странице скрипта «как в общих настройках» или свои значения.
4. Общие настройки.

Переопределение поключевое: у скрипта и расписания каждый ключ либо «наследовать», либо своё значение. У скрипта доступны все ключи; у расписания все, кроме `done_manual`.

Блок Telegram на странице скрипта и у расписания показывается, только если Telegram подключён; иначе ссылка «подключить в Настройках».

## Сообщения

Простой текст, без технических имён. Каждое начинается с названия скрипта (и пресета, если есть):

- итог: «Готово: <скрипт>», строка итога (`summary`, «48 из 50, 2 упали», `count`), длительность, время запуска, ссылки скрипта (`links`), файл `main` документом, если включено и он не больше 50 МБ (иначе только упоминание);
- падение: «Упал: <скрипт>», причина одной строкой (та же, что на экране запуска);
- тихая поломка: строкой в сообщении об итоге, как на главной;
- вопрос: текст вопроса, срок ответа.

Ссылки на экран запуска в приложении нет: у `dawg-replay ui` случайный порт и вход по токену, а токен в Telegram отправлять нельзя. Вместо неё в конце строка «В приложении: Запуски, <скрипт>, <время>».

Тексты проходят ту же маскировку, что журнал (`diagnosis.scrub`, значения секретов).

## Ответ на вопрос из Telegram

- `confirm` и `choice`: инлайн-кнопки. `text`: «ответьте на это сообщение» (reply), принимается и следующее простое сообщение, если ждёт ровно один вопрос.
- Связь сообщения с вопросом: `callback_data` содержит короткий ключ, по которому находится (`run_id`, `ask_id`); для reply хранится соответствие `message_id` → (`run_id`, `ask_id`). Где хранить, решает исполнитель (БД или файл в каталоге запуска).
- Ответ пишется тем же `asks.write_answer`, что ответ из UI и CLI. Первый ответ засчитывается; ответ на уже закрытый вопрос получает «Уже отвечено» или «Вопрос закрыт». После ответа сообщение с вопросом правится: «Ответ принят» (для секрета без значения).
- Секретный ответ разрешён: бот сразу удаляет сообщение пользователя с кодом (`deleteMessage`), ответ в журнал и события не попадает (как сейчас). Если удалить не удалось, бот пишет «удалите сообщение с кодом сами».
- Ответы принимаются только из привязанного `chat_id`.
- Один получатель обновлений на бота: `getUpdates` нельзя звать из нескольких процессов параллельно (Telegram возвращает конфликт), а несколько запусков могут ждать ответа одновременно (до `max_parallel_runs`, плюс UI). Нужен один опрашивающий на установку, например по файлу-блокировке в `<home>`, который раскладывает ответы по всем ждущим запускам; остальные процессы только отправляют. Конкретный механизм решает исполнитель, требование: ни один ответ не теряется и не уходит не тому запуску, при падении опрашивающего его роль подхватывает другой ждущий процесс.
- Опрос идёт, только пока хотя бы один вопрос ждёт ответа, и во время привязки чата.

## Надёжность

- Отправка в фоне от цикла `supervise`, с коротким таймаутом и одной-двумя повторными попытками; цикл запуска и отмена не ждут Telegram.
- Сообщение об итоге отправляется после `store.finish` и страховки браузеров. Потерянные (`recover_lost`) и не стартовавшие (`not_started`, `skipped`) запуски отправляет тот процесс, который их закрыл, синхронно с коротким таймаутом (несколько секунд), потому что это может быть короткая команда CLI. Не получилось: пометка «не отправлено», следующий процесс приложения, который закрывает запуски или стартует UI, пробует ещё раз; старше суток не отправляются. Повторно об одном запуске одно и то же не пишется (пометка в БД).
- «Первый ответ засчитывается» должен быть атомарным между UI, CLI и Telegram: `asks.write_answer` сейчас проверяет `exists()` и потом делает `os.replace`, это нужно заменить на атомарное создание (`O_EXCL` или `link`).
- Ошибки Telegram (неверный токен, бот заблокирован пользователем, сеть) пишутся строкой в журнал запуска и как «последняя ошибка» в блок Telegram в Настройках.

## Версии и приёмка

- dawg-replay 1.3.0, kit и контракт без изменений. Скилл: строка в `SKILL.md`, что у приложения теперь есть свои уведомления в Telegram (в Настройках), скрипту слать итог самому для этого не нужно; бамп плагина.
- Тесты без сети: фейковый Bot API (локальный HTTP-сервер или подмена транспорта), временное хранилище паролей.
- Приёмка руками: свой бот, расписание с вопросом-подтверждением и с секретным кодом, ответ из Telegram при закрытом UI, длинный ручной запуск с порогом, падение, отключение.

## На усмотрение исполнителя

Структура модуля (`telegram.py` и т.п.), хранение переопределений у скрипта и расписания, хранение соответствий сообщений и вопросов, механизм единственного опрашивающего, вёрстка блоков, точные тексты в рамках описанного.
